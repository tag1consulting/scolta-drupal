# Changelog

All notable changes to scolta-drupal will be documented in this file.

This project uses [Semantic Versioning](https://semver.org/). Major versions are synchronized across all Scolta packages; minor and patch versions are released independently per package.

## [Unreleased]

### Changed
- **The managed Amazee.ai gateway is now enabled explicitly from the AI settings screen instead of being configured automatically (`scolta.install`, `src/Service/ScoltaAiService.php`, `src/Form/ScoltaSettingsForm.php`, `src/Form/AmazeeSettingsForm.php`, `scolta.module`).** Enabling it is two deliberate acts, and nothing else does either of them: select **Amazee.ai (managed gateway)** as the AI provider, then follow the call to action on that screen and complete the connect flow. The settings screen says so while the provider is selected with nothing connected yet, so the state cannot be mistaken for a working one. **The stored connection is used only while `amazee` is the selected provider**, which is the substantive behaviour change: it was previously injected into AI traffic for every provider except `drupal_ai`, so an operator who selected `anthropic` and configured their own key still had that key shadowed by the stored connection, and `getApiKeySource()` answered `amazee` while their key was the one traffic would have used. Selecting any other provider now removes the stored connection and both credential-recovery markers, so nothing is left to shadow the operator's own key and nothing keeps prompting them to reconnect a gateway they have moved off — a state the UI previously offered no way to clear. The reconnect notice in `hook_page_top()` is gated on the selected provider for the same reason. The connect flow in `AmazeeSettingsForm` selects the provider on success, because a connection the selected provider cannot use would leave the operator told they are connected while AI kept running on something else. Model re-resolution against a connection that is **already stored** is the one gateway call left on the request path, and it is gated on all three of: the gateway selected, a connection stored, and the gateway-scoped model still unresolved — so a site with nothing stored makes no outbound call at all and degrades exactly as a wholly unconfigured site does (unexpanded, no summary, HTTP 200). The settings field also stops preselecting the gateway from a stored connection when no provider has been saved: a connection existing is not an operator choosing it.
- **`use scolta ai` is no longer granted to the anonymous role at install (`scolta.install`, `README.md`).** The three AI endpoints (`/api/scolta/v1/expand-query`, `/summarize`, `/followup`) make cost-bearing LLM calls, and the install-time grant left them reachable by unauthenticated traffic on every site that took the default; the per-IP and site-wide flood thresholds capped the rate but not the exposure. The authenticated grant stays, because logged-in AI search is the intended out-of-the-box behaviour. A site that wants anonymous AI search grants the permission at *Administration › People › Permissions*, and that decision stands — the update below runs once and does not revisit it.
- **`scolta_update_10004()` carries existing sites onto both rules (`scolta.install`).** A site holding a stored connection with no explicit key and a saved provider that is neither `amazee` nor `drupal_ai` has its provider set to `amazee`: under the old rule that connection was already serving its AI traffic, so this states what was true rather than changing where traffic goes, and the site does not lose AI at update time for a reason it cannot see. A site with an explicit key (environment variable, `settings.php`, or config) is left alone, because the explicit key always won and the stored connection was never serving anything. The same hook revokes `use scolta ai` from the anonymous role. Config-managed sites must re-export after running it, as `README.md` now describes, or `config:import` restores the old grant seconds after the hook removes it.
- **Coverage (`tests/src/Functional/ManagedGatewayOptInFunctionalTest.php`, `tests/src/ManagedGatewayOptInInstallTest.php`, `tests/src/ManagedGatewaySwitchAwayTest.php`, `tests/src/ScoltaAiServiceGatewayClientTest.php`, `tests/src/ModelResolutionSelfHealTest.php`, `tests/src/Functional/ScoltaApiKeySourceMatrixFunctionalTest.php`, `tests/src/Functional/AmazeeReauthNoticeTest.php`, `tests/src/Functional/AmazeeModelKeySeparationTest.php`, `tests/src/Functional/ScoltaEndpointFunctionalTest.php`, `tests/src/Functional/AiEndpointFloodFunctionalTest.php`, `tests/src/Functional/AiPermissionBackfillFunctionalTest.php`).** The behavioural tests build a real `ScoltaAiService` over the test site's own config and state, so they assert what would actually be sent rather than the shape of the source: a fresh install stores nothing and reports `none`; building a client with nothing stored writes nothing and produces no key; the stored connection reaches the client only with `amazee` selected and is absent under `anthropic`; the reported source is `amazee:operator` only when selected and stored; submitting the real settings form with a different provider clears the connection and both markers, while saving with the gateway still selected leaves it connected; the settings screen shows the connect call to action only while nothing is stored; and the update hook covers its four cases plus a second run. The key-source matrix gains the provider as a third dimension, including the two cells where a connection is stored and ignored. The file-inspection tests pin the structural properties the behavioural ones cannot: that `scolta.install` names no gateway machinery at all, that the request path can never call out on the strength of nothing being stored, and that the clear-on-switch helper removes the connection and both markers. Existing tests that asserted the old defaults were updated to the opt-in contract rather than deleted, including the ones that asserted anonymous visitors reach the AI endpoints; the flood test now authenticates, because the flood check lives in the controller behind the route permission and an anonymous request is refused before reaching it. Note that `scolta_update_10001()` is left exactly as it shipped: an update hook that has run on a site is a record of a step that site took, not a place to restate current policy.

### Fixed
- **A site connected to the managed AI gateway could not authenticate, because the stored token was never decrypted before it was used (`src/Service/ScoltaAiService.php`, `scolta.services.yml`).** The token is encrypted at rest by `DrupalConfigStorage::store()` and decrypted by its `load()`. `resolveApiKey()` did not go through `load()`: it built the credentials from the raw State array, so the value that became `ai_api_key`, and with it the bearer token on every request the AI client sent, was the ciphertext. The gateway rejected it, and message, expand and summarize all failed authentication on a connection that was otherwise valid. **Model names resolved normally throughout**, because the self-heal in `createClient()` already read through `load()`, so the failure looked selective rather than total and pointed away from the credential itself. `resolveApiKey()` now reads `$this->amazeeConfigStorage?->load()`, the one path that decrypts. Nothing else about the resolution changes: an explicit `SCOLTA_API_KEY` or `$settings['scolta.api_key']` still wins and still reports its own source, stored credentials that lost are still reported as stored, and a connection whose model resolution has not completed still degrades exactly as before. When the credential store is absent (the minimal construction path, where it is an optional argument) the resolution reads as no stored credentials, which is what an empty State entry already did. The Drupal state service is no longer a constructor argument of `ScoltaAiService` or an argument in `scolta.services.yml`, because the credential store is now the only route to the credentials and nothing else in the service read state. Covered by `tests/src/Functional/AmazeeStoredTokenDecryptionTest.php`, which stores a token through the real store, confirms the stored value is ciphertext, and asserts that both the resolved key and the `ai_api_key` in the built client config are the original plaintext; it fails against the pre-fix code.
- **The key-source matrix could not pass in CI, for a reason unrelated to what it tests (`tests/src/Functional/ScoltaApiKeySourceMatrixFunctionalTest.php`).** It set `SCOLTA_API_KEY` with `putenv()` and then asserted that `/health` and the settings page agreed with the in-process resolution. There are two processes: the functional job starts `php -S` before PHPUnit runs, so the server inherits nothing the test process does afterwards, and every env-only cell resolved to `env` in process and `none` over HTTP. The matrix failed on its first row on `main`. The variable is now also written into the test site's `settings.php`, which Drupal includes on every request, so the server observes the same state the assertions describe.
- **`getApiKeySource()` reported Amazee.ai while an explicit key served every request, because reporting and resolution were two derivations with opposite precedence (`src/Service/ScoltaAiService.php`, `src/Form/ScoltaSettingsForm.php`, `src/Controller/HealthController.php`, `src/Commands/ScoltaCommands.php`, [#188](https://github.com/tag1consulting/scolta-drupal/issues/188), parent [scolta-php#252](https://github.com/tag1consulting/scolta-php/issues/252)).** Root cause: `buildConfig()` gave an explicit `SCOLTA_API_KEY` or `$settings['scolta.api_key']` priority over stored Amazee credentials and fell through to Amazee only when both were empty — its own comment said so outright — while `getApiKeySource()`, which every reporting surface called, checked `scolta.amazee.credentials` **first** and returned `'amazee'` before it had looked at the environment at all. Nothing forced the two to agree, and they did not. A site with a perfectly valid key therefore sent every request with that key while the settings form displayed "Connected to Amazee.ai (auto-provisioned free trial)" in success green, and nothing in the interface revealed which key was actually in use. **The blast radius was wider than the message**, because `isAmazeeActive()` was defined as `getApiKeySource() === 'amazee'` and inherited the wrong precedence: it also drove the provider the settings form preselected and the `scolta:status` output. This is not cosmetic — it is a diagnostic surface lying in exactly the situation where somebody reaches for it, and it has already cost a misdiagnosis. On the Athenaeum demo on 2026-07-29 the Amazee message was read as evidence that the environment variable was missing, when a 109-character `sk-ant-api03` value was present in the container the whole time and the real defect was elsewhere. **The fix is a single derivation, not two that agree.** A new `resolveApiKey()` hands the platform's explicit candidates and any stored credentials to `Tag1\Scolta\Config\ApiKeyResolver` and returns the key, its source, the effective provider and the base URL together; `buildConfig()`, `getApiKey()`, `getApiKeySource()`, `isAmazeeActive()`, `createClient()`, the key-expiry-recovery gate, the settings form, `/health` and both Drush commands all read that one answer. Fixing `getApiKeySource()` to check the environment first would have made them agree today and left them free to drift again, which is why the resolver returns the source alongside the key: there is nothing left for a caller to re-derive. **`getApiKeySource()` now returns `amazee:auto` or `amazee:operator` rather than a single `amazee`** — a trial that provisioned itself and a provider somebody selected mean different things to an operator reading a status line — and both remain distinct from `env`, `settings` and `none`. **A stored-but-overridden credential is now stated rather than hidden:** the settings form appends "Amazee.ai credentials stored but overridden by SCOLTA_API_KEY" (or by the settings.php key) and renders the whole line in the warning colour, because showing that state in success green is what let it be read as proof that Amazee was serving traffic. `/health` gains `ai_key_source` and `ai_amazee_overridden`; `scolta:status` prints the source and a full description; `scolta:check-setup` takes the resolution so its AI-key row cannot word the key differently from the settings page. Two behaviours are deliberately preserved rather than tidied: `createClient()` now guards on "nothing configured and nothing stored" instead of `source === 'none'`, so a site whose provider is `drupal_ai` — for which Amazee is ineligible and the source is therefore `none` — still does not provision a trial on top of credentials it already has; and the `drupal_ai` exclusion itself moved from a branch in `buildConfig()` to an input of the resolution, so every surface sees the same eligibility rule the config path applies. Covered by `tests/src/Functional/ScoltaApiKeySourceMatrixFunctionalTest.php`, whose four-by-two matrix drives every source with and without stored credentials against a real Drupal and asserts the settings form, the `/health` payload and the CLI row agree in every cell, and by `tests/src/ApiKeySourceSingleDerivationTest.php`, which pins the structural property instead of the symptom: nothing outside the resolver reads the credential store or `SCOLTA_API_KEY`, and all three reporting surfaces call `resolveApiKey()`. Requires the resolver added in scolta-php 1.1.0; the `tag1/scolta-php` constraint is bumped when that release is tagged.
- **An Amazee.ai gateway model alias is no longer written into the operator-facing `ai_model` ([#187](https://github.com/tag1consulting/scolta-drupal/issues/187), parent [scolta-php#251](https://github.com/tag1consulting/scolta-php/issues/251)).** Amazee model resolution returns LiteLLM **gateway aliases** (`claude-4-5-sonnet`) that only the Amazee proxy accepts. `ScoltaAiService::createClient()` wrote them straight into `scolta.settings:ai_model` and `ai_expansion_model` — the keys an administrator uses to name a provider-native model — with no guard beyond a non-empty check, so the write clobbered an explicit choice as well as the shipped default. Once the trial expired or a direct provider key was configured, `ai_provider` became `anthropic` while `ai_model` still held a name Anthropic's API does not recognise, and AI degraded permanently behind a generic `ai_error` with nothing in it for an operator to search for. Observed live on the Athenaeum demo on 2026-07-29: `ai_provider=anthropic`, `ai_model=claude-4-5-sonnet`, `POST /api/scolta/v1/expand-query` returning HTTP 200 `{"degraded":true,"degraded_reason":"ai_error"}` while three sibling demos on the shipped default worked with the same key. Two new config keys, `amazee_model` and `amazee_expansion_model` (both defaulting to `''`, with schema entries), now hold gateway aliases; they are written only by model resolution and read only while Amazee credentials are the effective key, and `buildConfig()` substitutes them into the client config on that path. `ai_model` and `ai_expansion_model` are never touched by auto-resolution again. This is the shape the ADR on scolta-php#251 settled on, and the one scolta-laravel and scolta-node already use — the point of the parent issue being that four adapters were doing three different things. **The gateway keys have no settings-form field on purpose:** there is nothing to choose, and giving them one would recreate exactly the alias-versus-native-ID confusion this fixes.
- **The Amazee.ai trial form was the second binding site and is fixed with it (`src/Form/AmazeeSettingsForm.php`).** `submitStartTrial()` applied the same resolved names to `ai_model` / `ai_expansion_model`; its `=== ScoltaSettingsForm::DEFAULT_AI_MODEL` guard spared an explicit administrator choice but still parked a gateway alias in the shared key, where it survived a later provider switch just as the unguarded write did. It now writes the gateway keys, and the guard goes with it — there is no operator-chosen value in a gateway-scoped key to protect. Leaving this path alone would have reintroduced the bug for anyone starting a trial from the admin UI.
- **`modelIsResolved()`, the `hasResolvedModels:` predicate and the degraded-client guard all read the gateway key (`src/Service/ScoltaAiService.php`).** All three reasoned about `ai_model`; left there, the predicate would report "resolved" for any site whose administrator had named a model, and the half-provisioned self-heal would stop firing on precisely the sites that need it. The dated-default exclusion stays, because a site migrated by the update hook can carry it. `onModelsResolved` is now the named method `persistResolvedAmazeeModels()` rather than an inline closure, so a test can drive it without provisioning against the live control plane.
- **`scolta_update_10003()` migrates existing sites (`scolta.install`).** A site can already have an alias sitting in `ai_model`. The hook backfills the two gateway keys everywhere, and on a site with **stored Amazee credentials** — the only place the old callback could have written — moves a non-default `ai_model` into `amazee_model`, moves `ai_expansion_model` alongside it, and resets `ai_model` to the shipped default, logging and returning both values so the operator can see what moved. Amazee.ai keeps working across the update, because `amazee_model` is exactly where the gateway path now reads from. A site **without** credentials is left strictly alone: its `ai_model` may well be an explicit administrator choice, there is no way after the fact to tell one from an orphaned alias, and resetting it would recreate the bug being fixed — those sites are covered instead by the provider/model mismatch tripwire tracked on scolta-php#251. On a credentialed site the whole non-default value is treated as gateway-resolved rather than sniffed for alias shape, deliberately: the old callback wrote unconditionally so nothing an administrator chose could have survived there anyway, and the names come from whatever the gateway's `/model/info` returns, so no naming convention is stable enough to test against. Nothing is discarded either way.
- **Coverage at the layer that would have caught it (`tests/src/Functional/AmazeeModelKeySeparationTest.php`, `tests/src/Functional/AmazeeModelMigrationTest.php`, `tests/src/AmazeeModelKeySeparationTest.php`).** The behavioural tests build a real `ScoltaAiService` over the test site's own config and state, so they assert the model that would actually be sent rather than the shape of the source: the alias is sent while Amazee credentials are effective, the operator's native model is what a direct provider gets once they are gone (the expire-then-switch regression), an operator's native expansion model never leaks to the gateway, an explicit administrator choice survives a resolution run, and an empty resolved name does not blank a stored alias. All seven fail against the pre-fix code. A second functional file exercises the update hook across all six of its cases. They are functional rather than unit for a structural reason worth knowing before adding more of either: **the unit job declares `provide: {drupal/core: "11.2.0"}`, so no part of the framework is installed there** — that is what "tests run without a Drupal bootstrap" means, and it is why every unit test in this package is source or YAML inspection. `composer test` against the committed lock does have drupal/core in `vendor/`, so a unit test touching a `Drupal\Core\*` class passes locally and errors in CI. The unit file keeps what needs no framework: the two keys' install defaults and schema types, the absence of a settings-form field for them, each binding site's write target, and the migration hook's guards. Note for anyone running the functional suite: `scolta_install()` provisions and stores a **real** Amazee.ai trial whenever the runner can reach the control plane ([#195](https://github.com/tag1consulting/scolta-drupal/issues/195)), so a test about the uncredentialed case has to establish that state rather than assume it.

### Added
- **Search as you type, with all ten settings on the admin form (re-vendored `js/scolta.js` and `css/scolta.css`, `config/install/scolta.settings.yml`, `config/schema/scolta.schema.yml`, `config/scolta.settings.example.yml`, `src/Form/ScoltaSettingsForm.php`, `src/Plugin/Block/ScoltaSearchBlock.php`, `scolta.install`; [scolta-php#247](https://github.com/tag1consulting/scolta-php/pull/247)).** Typing in the search box now opens a suggestions dropdown underneath it. Typing alone still never runs a search: the full pipeline (AI expansion, merge, facet counts, AI overview, follow-ups) waits for Enter, the search button, or a selected suggestion, and the suggest path never writes `#scolta-results`, the facet panel, or the URL. **No index rebuild is needed** — suggestions read the same fragments the result list does, so the feature works against an index built by any earlier release. The behavior is entirely in the vendored bundle; what this release adds on the Drupal side is the settings surface around it. Ten new top-level config keys with schema entries, install defaults byte-equal to the bundle's own fallbacks, and a **Search as you type** section on the settings form: `sayt_enabled` (`true`), `sayt_min_chars` (`2`), `sayt_debounce_ms` (`150`), `sayt_max_suggestions` (`6`), `sayt_recent_searches` (`true`), `sayt_max_recent` (`3`), `sayt_expand` (`true`), `sayt_expand_per_minute` (`6`), `sayt_expansion_delay_ms` (`500`), `sayt_suggestion_action` (`navigate`). `sayt_enabled: false` restores the pre-existing widget exactly — no dropdown, no combobox roles on the input, no browser storage read or written on any path. `sayt_suggestion_action` chooses whether selecting a title suggestion opens that result (a real anchor, so middle-click and "copy link address" work) or runs the full search for its title; a recent-search suggestion always runs the search, because navigating to a stored query string is meaningless, and an unrecognized value clamps to `navigate` in both the form and the bridge. The enrichment cap is not an arbitrary throttle and the form says so: suggestion-driven expansions share the AI flood budget with committed searches, so an unbudgeted suggest path would spend a visitor's per-IP allowance on prefixes they never submitted and leave the search they actually ran with no expansion and no overview. `css/scolta.css` is re-vendored in the same commit for the dropdown styles. Both files copied byte-identically from the canonical `scolta-php/assets/`, verified with `cmp`; the WASM pair was already current and is untouched.
- **`ScoltaSearchBlock::build()` now bridges the ten SAYT keys into `drupalSettings.scolta`.** The block hand-builds the settings array rather than emitting `ScoltaConfig::toBrowserConfig()` wholesale, so a new browser key does not arrive by itself — `hideEmptyFacets` is bridged the same way, one line at a time. The values are read from Drupal config rather than off `ScoltaConfig`, deliberately: SAYT ships in the bundle this module vendors and commits, so the feature must work against any `tag1/scolta-php` in the supported `^1.0` range without a constraint bump, and the defaults in the bridge repeat the install defaults so a site that has not yet run the update hook still gets the documented behavior. `tests/src/Functional/BrowserConfigParityFunctionalTest.php` is what makes a missed key impossible to ship: it diffs the emitted key set against the keys parsed out of the committed bundle in both directions, and the re-vendored bundle reads all ten as `instanceConfig.sayt*`.
- **`scolta_update_10002()` gives existing sites the SAYT defaults (`scolta.install`).** `config/install/scolta.settings.yml` only ever runs on a fresh install, so a site updating into this release would have none of the ten keys. The bundle falls back to its own hardcoded defaults for an absent key, and those equal the shipped ones — so the feature would appear to work while the settings form displayed values that existed nowhere in config, and the first save would silently start writing keys that had never been there. The update writes only keys that are absent, tested for with `=== NULL` rather than a falsy check, so a site that set any of them ahead of the update keeps its value — including a deliberate `sayt_enabled: false`, which an `empty()` guard would have quietly switched back on. It returns a summary naming what it added, and reports "already configured" when there is nothing to do. `README.md` gains a **Search as you type** section covering the defaults, the off switch, the CJK note on `sayt_min_chars`, why the enrichment cap exists, and the `drush updatedb` / `drush cex` path for config-managed sites.
- **Coverage for the whole path (`tests/src/SaytSettingsTest.php`, `tests/src/Functional/SaytSettingsFunctionalTest.php`).** Every failure mode here is silent, because the bundle's fallbacks equal the shipped defaults: a field that saves nothing, a saved value the block never bridges, a bridged value the reloaded form does not show, and an update hook that clobbers an opt-out all look exactly like a working feature on a default site. The functional tests therefore lean on the non-default direction — SAYT off, the other suggestion action, numbers nothing would produce by accident — submitting the real form (so a wrong field name is caught) and asserting on `drupalSettings` from a separate node render (so a missing bridge is caught), plus the update hook's three cases: absent keys added, existing values including `false` left alone, a second run a no-op. The file-inspection tests pin the ten defaults across install config, schema types, the example file, the form fields and their bounds, the block's emitted keys, and the update hook's absence guard, and assert the committed bundle actually reads each key it is sent.
- **Re-vendored the browser bundle (`js/scolta.js`): a platform render seam, so a Drupal site can supply its own result markup instead of Scolta's card ([scolta-php#246](https://github.com/tag1consulting/scolta-php/pull/246)).** Three additions in the canonical bundle, none of which change anything for a site that does not use them. **(1)** Four render lifecycle events on the elements Scolta writes, bubbling and non-cancellable: `scolta:before-results-render` (`{container, reason}`) and `scolta:results-rendered` (`{container, results, rendered, reused, appended, query}`) around every write to `#scolta-results`, and `scolta:before-filters-render` / `scolta:filters-rendered` around the `#scolta-filters` write. `reason` distinguishes the "Searching..." placeholder, the primary paint, the post-expansion repaint and the "show more" append, so a behaviour can detach before its nodes are destroyed and re-attach after. **(2)** `Scolta.setResultRenderer(fn)` (plus a per-instance form), which replaces the built-in card with `fn(data, ctx) -> string | null`; returning `null` falls back to the built-in card for that result alone. `ctx` hands over the already-escaped, `<mark>`-wrapped excerpt, title, and a scheme-neutralized URL, so the excerpt survives into markup that has no excerpt region of its own — the shape a Drupal integration needs to swap in a rendered entity view mode. It is a registration function rather than a config key precisely so nothing has to travel through `drupalSettings`, and this re-vendor therefore adds no Drupal setting and no schema entry. **(3)** `init()` no longer runs `root.innerHTML` over the mount point, so server-rendered markup inside the search container survives — the bug that bit this adapter specifically, because the block calls `Scolta.init()` directly and bypassed the `autoInit()` guard that had been holding the line. Also in this bundle: the repaint after AI query expansion now reconciles the result list by identity instead of replacing it, so an expansion that reorders nothing moves no DOM node. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js`, verified with `cmp`. Note that CI does not verify this: `composer update` fires `post-update-cmd` → `copy-assets`, which overwrites `js/scolta.js` from the vendored scolta-php before the "Verify duplicated assets match canonical" step runs, so that step compares a file Composer just wrote against the manifest of the source it wrote it from and can never fail on a stale committed copy. The adapter suites in CI therefore exercise scolta-php `main`'s bundle, not this one; the bundle in this PR was exercised locally through the `../scolta-php` path repo (816 tests).
- **The six specificity and co-occurrence ranking settings are now configurable from Drupal (`config/schema/scolta.schema.yml`, `config/install/scolta.settings.yml`, `config/scolta.settings.example.yml`, `src/Form/ScoltaSettingsForm.php`).** `scoring.specificity_weighting` (bool, default on), `scoring.specificity_floor` (`0.15`), `scoring.specificity_strong_match` (`0.55`), `scoring.specificity_cooccurrence` (`0.9`), `scoring.specificity_agreement_gate` (`0.45`) and `scoring.specificity_agreement_decay` (`1.0`) get schema entries, install defaults, settings-form fields in the Scoring section, and save-handler mappings. The browser has read all six for some time and scolta-php now carries all six as typed properties, but no Drupal setting existed for any of them, so every site was pinned to the hardcoded JS fallbacks. Defaults are byte-equal to those fallbacks, so an existing site's ranking does not move; `specificity_cooccurrence: 0` scores each result purely by its single best-matching sub-query. Install defaults are asserted in `tests/src/ScoltaAiServiceTest.php`, and `tests/src/YamlIntegrityTest.php` already enforces the schema-to-install one-to-one in both directions.
- **A browser-config parity guard, so a key the bundle reads can no longer be settable from nowhere (`tests/src/Functional/BrowserConfigParityFunctionalTest.php`).** Root cause of the gap above and of several like it across the Scolta packages: nothing asserted that the config a platform emits covers what `js/scolta.js` reads off it, so a browser-side read could exist with no corresponding setting and CI stayed green, because an unsettable key silently falls back to its hardcoded JS default and the feature merely appears not to work. The new functional test renders a node page carrying the search block, extracts `drupalSettings.scolta`, and diffs its key set against keys parsed out of the committed bundle in both directions, recursing one level into `scoring` and `endpoints` so a missing sub-key cannot hide behind a passing top-level check. It must be functional rather than unit: the settings array is built inside `ScoltaSearchBlock::build()`, so only a rendered page gives the real emitted config. Forward allowlist is `priority_pages` alone (caller-supplied through the scolta-php `createInstance()` API, emitted by no adapter); reverse allowlist is `container` alone (read only by `autoInit()` off the global, never off the instance config). Three tripwire assertions on the extracted counts run before any diff, so a reformat of the bundle that breaks the extraction fails loudly instead of passing while asserting nothing.
- **Regression coverage for the `hide_empty_facets` bridge (`tests/src/Functional/ScoltaSettingsFormFunctionalTest.php`).** The setting shipped with schema, install default, form checkbox, save handler and block bridge but zero test coverage. Two tests close that: a full form round-trip that unticks the checkbox, asserts the saved config is `false`, then renders a node page and asserts `"hideEmptyFacets":false` reaches `drupalSettings`; and a default-path test asserting `"hideEmptyFacets":true`. The false direction is the load-bearing one, because the browser default is to hide, so a bridge that dropped the value entirely would still look correct in the on state. The round-trip is deliberate too: the settings page carries no search block, so submitting the form and asserting on that response would find no `drupalSettings.scolta` at all, and the config-set shortcut used by the older block tests would not catch a form-field-name typo.

### Added
- **Playwright layout tests** (`tests/playwright/layout.spec.js`): Three browser-level tests at 1440 px viewport asserting `.scolta-layout` fills ≥90 % of viewport width in single-column and two-column (`has-filters`) modes. Wired into CI (`playwright` job in `.github/workflows/ci.yml`).
- **Admin rebuild notice persistence**: Rebuild notices now persist in Drupal State across page loads until each admin user explicitly dismisses them. Per-user dismissal tracked via `user.data` service keyed to a unique `notice_id`; notices render via `hook_page_top()` on admin pages. Dismiss route: `GET /admin/config/search/scolta/dismiss-rebuild-notice?notice_id=…`.
- **Drupal functional test suite in CI** (`functional` job in `.github/workflows/ci.yml`): Boots a real Drupal 11 installation (SQLite + PHP built-in server) and runs all `tests/src/Functional/` tests on every push. Covers the full HTTP render pipeline, including `hook_page_top()` and controller instantiation, which unit tests cannot reach.
- **`RouteSmokeFunctionalTest`**: Reads `scolta.routing.yml` at runtime and smoke-tests every defined route — GET routes as authenticated admin (assert non-500), GET routes as anonymous (assert 302/403), POST routes with empty body (assert structured JSON 4xx). Any route added to the YAML is automatically covered on the next CI run without a manual test-list update.
- **`YamlIntegrityTest::testAllFromRouteCallsReferenceDefinedRoutes`**: Static-analysis guard that scans all `.module` and `src/` PHP files for `fromRoute('scolta.*')` calls and asserts each name exists in `scolta.routing.yml`. Catches the `RouteNotFoundException` class of bug at the unit-test level before a browser ever hits the page.

### Changed
- Inherits all scolta-php 0.2.4 fixes and features (phrase-proximity scoring, WASM config key fix, quoted-phrase forced-mode, second WASM rebuild)

### Fixed
- **Full-width search results layout**: `css/scolta.css` had `grid-template-columns: 220px minmax(0, 1fr)` as the permanent default for `.scolta-layout`, making the empty filter sidebar always occupy 220px and squeezing all results into the narrow right column. The layout now defaults to `grid-template-columns: 1fr`; the two-column variant only activates via `.scolta-layout.has-filters` (added by JS when multiple sites are indexed). Added `.scolta-filters:empty { display: none }` so the empty sidebar is hidden. Adds `LayoutCssRegressionTest` to guard against recurrence.

## [0.2.3] - 2026-04-17

### Fixed
- **Asset deployment on install**: `hook_install()` now copies compiled JS/CSS/WASM from `scolta-php` into the module directory. Composer `post-install-cmd` scripts only run for the root package, so assets were never deployed when installing as a dependency.
- **Pagefind path fix**: `ScoltaSearchBlock` was pointing `pagefindPath` at `{output_dir}/pagefind.js`; the Pagefind binary writes its output into a `pagefind/` subdirectory, so the correct path is `{output_dir}/pagefind/pagefind.js`.
- **Cache invalidation after rebuild**: All rebuild paths (Drush, admin UI form, Batch API, Queue Worker) now invalidate the `scolta_search_index` cache tag so the search block updates immediately without a manual cache flush.

### Changed
- Inherits all scolta-php 0.2.3 fixes and features (filter sidebar, N-set merge, AI context, PII sanitization, priority pages)

## [0.2.2] - 2026-04-16

### Added

- **Scoring language:** Settings form now includes a language select (30 ISO 639-1 options) stored as `scoring.language`.
- **Custom stop words:** Textarea field for comma-separated additional stop words (`scoring.custom_stop_words`).
- **Recency strategy:** Select field for recency decay function — `exponential`, `linear`, `step`, `none`, or `custom` (`scoring.recency_strategy`).
- **Custom recency curve:** Textarea for JSON `[[days, boost], …]` control points, visible only when strategy is `custom` (`scoring.recency_curve`).
- Config schema (`scolta.schema.yml`) and install defaults (`scolta.settings.yml`) updated for all four new fields.

## [0.2.1] - 2026-04-15

### Fixed

- **Security:** Validate the configured Pagefind binary path against an allowlist (`pagefind`, `npx`, `node_modules/.bin/pagefind`) before passing to `Process`. Rejects unexpected paths and logs an error, preventing command injection via a compromised config value.

## [0.2.0] - 2026-04-13

### Fixed

- **UX:** `hook_requirements()` added to `scolta.install` — shows a warning in the Drupal Status Report when the Pagefind binary is not installed and the PHP fallback indexer is active, with instructions to install the binary for full language support.

### Added

- **Install hook**: `hook_install()` queues an initial index build on install and displays a status message with instructions for immediate building via Drush.
- **Index-missing validation in search block**: `ScoltaSearchBlock::build()` checks for the Pagefind index on disk; admins see a warning with a link to build, non-admins see nothing until the index is ready.
- **Rebuild Index button**: Admin settings form at `/admin/config/search/scolta` now includes a "Rebuild Index" button that triggers an immediate index rebuild using Batch API (PHP indexer) or synchronous binary execution.
- **Batch API integration**: PHP indexer rebuilds from the admin UI use Drupal's Batch API (`ScoltaBatchOperations`) to process content in chunks, preventing timeouts on large sites.
- **Queue Worker for auto-rebuild**: New `ScoltaRebuildWorker` queue worker (`scolta_rebuild` queue) processes index rebuild requests during cron, with a lock to prevent concurrent builds.
- **Auto-rebuild on entity changes**: `hook_entity_insert()` and `hook_entity_update()` automatically enqueue a rebuild when nodes are saved and `pagefind.auto_rebuild` is enabled.
- **Uninstall cleanup**: `hook_uninstall()` cleans up the rebuild queue, build lock, and state entries when the module is uninstalled.
- **PHP indexer integration**: `scolta:build` now supports in-memory PHP indexing via `Tag1\Scolta\Index\PhpIndexer`, eliminating the need for the Pagefind binary.
- `--indexer` option on `scolta:build` to select indexer mode (`php`, `binary`, or `auto`); overrides the `indexer` config setting.
- `--force` option on `scolta:build` to skip the content fingerprint check and force a rebuild.
- `indexer` config key (`auto`/`php`/`binary`) in `scolta.settings.yml` with matching schema entry.
- Auto-detection: when `indexer` is `auto`, the build command uses the binary if available, otherwise falls back to the PHP indexer.
- Content fingerprint tracking (`.scolta-state` file) to skip unnecessary rebuilds when content has not changed.
- `wasmPath` key added to `drupalSettings.scolta` in `ScoltaSearchBlock`, pointing to the WASM glue JS file served from the module directory.
- `ai_languages` config setting for multilingual AI response support, configurable via the admin form (comma-separated language codes)
- All AI controllers now pass `aiLanguages` from config to `AiEndpointHandler`
- `PromptEnrichEvent` Symfony event dispatched before AI prompts are sent to the LLM provider
- `EventDrivenEnricher` bridging scolta-php's `PromptEnricherInterface` with Drupal's event system
- All AI controllers now inject the event dispatcher and pass the enricher to `AiEndpointHandler`

### Removed

- **Extism/FFI dependency**: All references to `ScoltaWasm`, `ExtismCheck`, `Tag1\Scolta\Wasm`, FFI, and Extism have been removed. scolta-php is now pure PHP with no native extensions required.
- FFI extension removed from CI workflow (`setup-php` no longer requests `ffi`).
- `continue-on-error` removed from CI lint step so lint failures are caught.
- `testScoltaPhpWasmPathUsesUnderscores` test removed (ScoltaWasm.php no longer exists in scolta-php).
- `isExtismAvailable()` helper and associated skip logic removed from `ScoltaSettingsFormTest` since `toJsScoringConfig()` is now pure PHP.

### Changed

- **Client-side WASM scoring**: Scoring, merging, and query expansion parsing now happen entirely in the browser via WASM instead of server-side PHP/WASM. The `wasmPath` setting is injected into `drupalSettings` so `scolta.js` can load the WASM glue module.
- WASM assets (`scolta_core.js`, `scolta_core_bg.wasm`) are now copied to `js/wasm/` by the `copy-assets` composer script alongside the existing JS/CSS assets.
- `scolta:build` Drush command now pre-resolves and caches all prompt templates (Step 3) after building the Pagefind index, reducing runtime overhead for API endpoints.
- Prompt resolution uses pure PHP (`DefaultPrompts::resolve()`) instead of WASM calls.
- Updated PHPDoc comments to remove stale references to WASM/FFI/Extism.

### Previously added

- Search API backend (`ScoltaBackend`) for Pagefind-based indexing and search
- 7 Drush commands: `scolta:build`, `scolta:export`, `scolta:rebuild-index`, `scolta:status`, `scolta:clear-cache`, `scolta:download-pagefind`, `scolta:check-setup`
- Admin settings form at `/admin/config/search/scolta` with AI, scoring, display, cache, and prompt configuration
- Search block (`ScoltaSearchBlock`) for placing the search UI in block regions
- 4 API endpoints: `expand-query`, `summarize`, `followup`, `health` at `/api/scolta/v1/`
- `DrupalCacheDriver` implementing `CacheDriverInterface` for Drupal's cache API
- Content export pipeline integrating Search API indexing with Pagefind HTML generation
- Drupal permissions: "Administer Scolta" and "Use Scolta AI features"
- Config schema and install defaults in `config/schema/` and `config/install/`
- Symlinked shared assets from scolta-php (`scolta.js`, `scolta.css`)
- Drupal behavior bridge (`scolta-drupal-bridge.js`) for Drupal.behaviors integration
