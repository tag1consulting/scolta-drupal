# Changelog

All notable changes to scolta-drupal will be documented in this file.

This project uses [Semantic Versioning](https://semver.org/). Major versions are synchronized across all Scolta packages; minor and patch versions are released independently per package.

## [Unreleased]

### Added
- **The six specificity and co-occurrence ranking settings are now configurable from Drupal (`config/schema/scolta.schema.yml`, `config/install/scolta.settings.yml`, `config/scolta.settings.example.yml`, `src/Form/ScoltaSettingsForm.php`).** `scoring.specificity_weighting` (bool, default on), `scoring.specificity_floor` (`0.15`), `scoring.specificity_strong_match` (`0.55`), `scoring.specificity_cooccurrence` (`0.9`), `scoring.specificity_agreement_gate` (`0.45`) and `scoring.specificity_agreement_decay` (`1.0`) get schema entries, install defaults, settings-form fields in the Scoring section, and save-handler mappings. The browser has read all six for some time and scolta-php now carries all six as typed properties, but no Drupal setting existed for any of them, so every site was pinned to the hardcoded JS fallbacks. Defaults are byte-equal to those fallbacks, so an existing site's ranking does not move; `specificity_cooccurrence: 0` scores each result purely by its single best-matching sub-query. Install defaults are asserted in `tests/src/ScoltaAiServiceTest.php`, and `tests/src/YamlIntegrityTest.php` already enforces the schema-to-install one-to-one in both directions.
- **A browser-config parity guard, so a key the bundle reads can no longer be settable from nowhere (`tests/src/Functional/BrowserConfigParityFunctionalTest.php`).** Root cause of the gap above and of several like it across the Scolta packages: nothing asserted that the config a platform emits covers what `js/scolta.js` reads off it, so a browser-side read could exist with no corresponding setting and CI stayed green, because an unsettable key silently falls back to its hardcoded JS default and the feature merely appears not to work. The new functional test renders a node page carrying the search block, extracts `drupalSettings.scolta`, and diffs its key set against keys parsed out of the committed bundle in both directions, recursing one level into `scoring` and `endpoints` so a missing sub-key cannot hide behind a passing top-level check. It must be functional rather than unit: the settings array is built inside `ScoltaSearchBlock::build()`, so only a rendered page gives the real emitted config. Forward allowlist is `priority_pages` alone (caller-supplied through the scolta-php `createInstance()` API, emitted by no adapter); reverse allowlist is `container` alone (read only by `autoInit()` off the global, never off the instance config). Three tripwire assertions on the extracted counts run before any diff, so a reformat of the bundle that breaks the extraction fails loudly instead of passing while asserting nothing.
- **Regression coverage for the `hide_empty_facets` bridge (`tests/src/Functional/ScoltaSettingsFormFunctionalTest.php`).** The setting shipped with schema, install default, form checkbox, save handler and block bridge but zero test coverage. Two tests close that: a full form round-trip that unticks the checkbox, asserts the saved config is `false`, then renders a node page and asserts `"hideEmptyFacets":false` reaches `drupalSettings`; and a default-path test asserting `"hideEmptyFacets":true`. The false direction is the load-bearing one, because the browser default is to hide, so a bridge that dropped the value entirely would still look correct in the on state. The round-trip is deliberate too: the settings page carries no search block, so submitting the form and asserting on that response would find no `drupalSettings.scolta` at all, and the config-set shortcut used by the older block tests would not catch a form-field-name typo.
- **`hide_empty_facets` setting to control zero-count facet visibility (`config/schema/scolta.schema.yml`, `config/install/scolta.settings.yml`, `src/Form/ScoltaSettingsForm.php`, `src/Plugin/Block/ScoltaSearchBlock.php`, re-vendored `js/scolta.js`; [scolta-php#239](https://github.com/tag1consulting/scolta-php/pull/239)).** The re-vendored bundle hides a facet value whose count is zero for the current query by default (dropping a filter group whose values are all zero); an active value stays visible so it can be unchecked. New top-level boolean config `hide_empty_facets` (default `true`), exposed as a checkbox in the settings form's Display section, mapped to `ScoltaConfig::$hideEmptyFacets`, and bridged to `window.scolta.hideEmptyFacets` by the search block. Set it to off to restore the prior behavior — every value renders, a zero-count one as a disabled `(0)` option. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js`; requires the matching scolta-php in `composer.lock` for the asset-parity CI check to pass.

### Changed
- **Re-vendored the browser bundle (`js/scolta.js`) from scolta-php: every query stopped running its Pagefind search twice, and the result list no longer waits for the facet counts ([scolta-php#244](https://github.com/tag1consulting/scolta-php/pull/244)).** Two independent defects in the bundle, measured on a production-size Pagefind index (109,308 indexed pages, 3,970 distinct filter values across 10 dimensions). **(1)** The facet-count pass derives its filters by keeping only the structural dimensions out of the active ones, so with no user-facing facet applied — the common case — it issued a search byte-identical to the primary one, and on the OR-fallback path it re-ran a per-term search for every term the result path had just searched. That doubled the cost of every query, because once Pagefind's filter chunks are loaded every search also computes per-value counts across every distinct filter value (roughly 1.45 ms per matched result). Identical searches are now memoized for the duration of one search cycle, keyed on the query plus the resolved Pagefind options, so a search whose scope genuinely differs still runs and the facet counts are unchanged. **(2)** The results were rendered only after that second search returned (for the query `math`: finished in memory at 24,558 ms, painted at 35,626 ms). They now paint as soon as they are ready and the filter panel is re-rendered when the counts land, behind a staleness re-check so a superseded query's late counts never repaint the panel; the panel holds its last painted state during the gap rather than flashing. Keystroke to first results on that corpus: `fractions` 4,011 -> 2,075 ms, `math` 22,254 -> 11,083 ms, a six-word query that falls back to OR 93,255 -> 46,584 ms. Neither change alters what the facet counts contain or how many results are returned. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js`; nothing in this package changed behavior.
- **Re-vendored the browser bundle (`js/scolta.js`) from scolta-php: co-occurrence ranking, and the co-occurrence path no longer loads full documents for non-seeding terms ([scolta-php#238](https://github.com/tag1consulting/scolta-php/pull/238), issue [#156](https://github.com/tag1consulting/scolta-php/issues/156)).** A document that agrees with several query and expansion terms now outranks one matching a single strong term. The user's typed words and the discriminating sub-words of an expansion phrase lend co-occurrence credit without introducing documents of their own, and their agreement is decided from result ids rather than loaded document fragments, so the seeded documents are joined by Pagefind entry id and the discarded loads that had inflated the per-query loaded-document count are gone. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js`; no Drupal-side code changed. Requires the matching scolta-php in `composer.lock` for the asset-parity CI check to pass.
- **Re-vendored the browser bundle (`js/scolta.js`) from scolta-php: partial matches are now ranked by term specificity so a common word stops flooding the head of the list.** A high-frequency word — typed, or leaked from an expansion phrase — used to pull off-intent documents to the top because the ranker rewarded matching it as much as matching the rare terms that carry the intent. Each partial-match sub-query (OR fallback, expansion terms, expansion sub-words) is now damped by an inverse-document-frequency weight from the term's own scoped Pagefind match count, so a rare term keeps full weight and a ubiquitous one is floored. The OR-fallback banner and the AI-summary hedge stop framing a strong result set as a failure when a high-specificity term matched, and `renderFilters()` hides zero-count facet values so a high-cardinality facet no longer buries the useful ones. Gated by the new `specificityWeighting` config (default on) with `specificityFloor` / `specificityStrongMatch` tunables. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js`; no Drupal-side code changed. Requires the matching scolta-php in `composer.lock` for the asset-parity CI check to pass.
- **Re-vendored the browser bundle (`js/scolta.js`) from scolta-php: Pagefind index chunks are now preloaded while the user types** ([tag1consulting/scolta-php#232](https://github.com/tag1consulting/scolta-php/pull/232), issue [#191](https://github.com/tag1consulting/scolta-php/issues/191)). Scolta runs no search until Enter or the search button, so every submitted search also paid for fetching the alphabetical index chunk(s) for the typed term. The search input now hands the term to `pagefind.preload()` — the chunk-resolution half of a search, which bails out before scoring — behind a 150 ms trailing debounce, a 2-character floor, a repeat-term skip, and a feature-detect on `preload` (index builds from Pagefind releases that predate it are unaffected). Failures are swallowed, so a cache warm can never break the search box. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js`; no Drupal-side code changed.
- Opened 1.0.6-dev development cycle.

### Fixed
- **Re-vendored `js/scolta.js` and the bundled scolta-core WASM from scolta-php.** Picks up the identifier/proper-noun search fix: expand_query rule 16 (NAMED ENTITY / EVENT → DEFINING DETAILS), summarize/follow_up grounding rules that forbid claiming the collection lacks content the model cannot see, and the new `[No result matched the full query; ...]` context marker that tells the summarizer when it is looking at an OR-fallback result set.
- **Drupal AI module provider path was completely broken — every AI feature failed with "Summary unavailable" ([#163](https://github.com/tag1consulting/scolta-drupal/issues/163)).** `ScoltaAiService::messageViaDrupalAi()` and `conversationViaDrupalAi()` treated `AiProviderPluginManager::getDefaultProviderForOperationType('chat')` as a string plugin ID, but it returns an array (`['provider_id' => …, 'model_id' => …]`). Passing that array to `createInstance()` threw `TypeError: Cannot access offset of type array` inside the plugin manager; `tryFrameworkAi()`/`tryFrameworkConversation()` swallowed it and fell back to the built-in HTTP client, so on the `drupal_ai` path (with no `SCOLTA_API_KEY` set — the expected state when the operator has chosen the Drupal AI module) summarize, expand-query, and followup all returned errors and the search UI showed "AI Overview — Summary unavailable." Both methods now unpack `provider_id` (passed to `createInstance()`) and `model_id` (passed to `chat()`, so the admin's configured model is honored instead of an empty string). The existing `ScoltaAiServiceDrupalAiServiceLayerTest` file-inspection guards asserted the buggy shape (`->chat($input, '', …)`) and could never catch this; they now pin the array-unpacking contract (`createInstance($default['provider_id'])`, resolved `model_id`, and that the raw array is never passed to `createInstance()`). A new `ScoltaAiServiceDrupalAiBehaviorTest` adds the runtime coverage that was missing: it actually executes `messageViaDrupalAi()`/`conversationViaDrupalAi()` against a fake plugin manager returning the real `['provider_id' => …, 'model_id' => …]` shape, and fails against the array-to-`createInstance()` call while passing against the fix. The same fix also corrects the token-limit call: the third `chat()` argument is `$tags`, not options, so the previous `['max_tokens' => $maxTokens]` passed there was silently ignored and never bounded the response. `max_tokens` is now applied via `$provider->setConfiguration()` before the call (with `['scolta']` passed as the tags), and the behavior test asserts the limit lands on `setConfiguration()`, that `chat()` receives the tags, and that the requested operation type is `'chat'`.

## [1.0.5] - 2026-06-27

### Fixed
- **Functional CI job no longer breaks when new Drupal core security advisories are published.** The `functional` job builds a disposable `drupal/drupal:11.3.10` site and `composer require`s the module into it. Composer 2.9 excludes advisory-flagged packages from the solver pool (`audit.block-insecure`), so the pinned core stopped resolving the instant SA-CORE-2026-005..009 were published — failing every PR (and `main`) with no code change. The throwaway test site now sets `composer config audit.block-insecure false` before install, so the smoke test is decoupled from latest-core advisory churn. This only affects the scratch `/tmp/drupal` harness; the audit gate on the shipped module is unchanged.
- **CI asset-drift guard now verifies the WASM pair in its manifest-absent fallback, not just `scolta.js`.** The "Verify duplicated assets" CI step is manifest-driven: when scolta-php ships `assets/ASSETS.sha256` it checksums all four canonical runtime assets (`js/scolta.js`, `css/scolta.css`, `js/wasm/scolta_core.js`, `js/wasm/scolta_core_bg.wasm`) and is correct. But its backward-compat fallback — taken when the vendored scolta-php predates the manifest — checksummed **only `js/scolta.js`** and then `exit 0`'d, so a sync that refreshed the JS but left `scolta_core.js` / `scolta_core_bg.wasm` (or `scolta.css`) stale passed CI. That JS-only verification path is the class of gap behind demos shipping a stale browser WASM scorer. The fallback now verifies **every** canonical asset directly against the vendored scolta-php source (`vendor/tag1/scolta-php/assets/<rel>`), covering the WASM glue + binary pair and the CSS, so a stale WASM can no longer slip through regardless of which branch runs. Guarded by `StructuralIntegrityTest::testAssetVerifyStepChecksumsWasmPair`, which asserts the fallback branch references `scolta_core.js`, `scolta_core_bg.wasm`, and `scolta.css` (it fails against the old `scolta.js`-only fallback). The Composer `copy-assets` hook and the manifest-present branch already covered all four assets and are unchanged.

### Added
- **CI now validates the drupal.org distribution tarball (`dist-archive` job).** Drupal.org builds the canonical project tarball from `git archive` semantics on its GitLab mirror, honoring `.gitattributes export-ignore` — but nothing in CI ever inspected what actually landed in that tarball, so a typo'd export-ignore line could ship developer cruft to every site (the scolta-wp 13 MB zip / WordPress.org dist-cruft flags are the precedent), and an over-broad line could silently drop a runtime asset and ship a dead module. New `scripts/validate-dist-archive.sh` (runnable locally) reproduces the `git archive HEAD` build and asserts: (1) no export-ignored path (`.github/`, `tests/`, `phpstan.neon`, `phpstan-baseline.neon`, `phpunit.xml`, `phpunit-functional.xml`, `phpcs.xml.dist`, `.gitattributes`, `.gitignore`, `.editorconfig`, `CLAUDE.md`, `scripts/`) leaked in; (2) every committed runtime asset is present (the `js/`, `css/`, `config/`, `src/` payload plus the `*.module`/`*.install`/`*.info.yml`/`composer.json` files); (3) a **fail-closed** top-level allowlist sweep — any new top-level file or dir fails CI until it is either export-ignored or explicitly added to the allowlist (the change-control gate); and (4) a size cap (measured clean archive ~2.0 MB, cap at ~2x = 4.2 MB). The current archive is clean — no leaks found.

### Fixed
- **Amazee.ai AI configuration now self-heals when stored credentials lack resolved model names.** An incomplete credential state could previously leave the AI path unavailable until a later step; it now recovers on a subsequent request, reusing the already-stored credentials, and otherwise degrades gracefully (unexpanded query / no summary, HTTP 200) instead of failing hard. The off (no-credentials) and explicit-key paths are unchanged. Built on scolta-php 1.0.5. Covered by `ModelResolutionSelfHealTest`.
- **Expired or revoked Amazee.ai credentials now recover instead of silently killing AI, and `/health` tells the truth.** The AI path detects unusable credentials, recovers automatically on a later request (guarded to one attempt per window), and retries once with refreshed credentials — wired only on the managed Amazee path, so an explicit `SCOLTA_API_KEY`/`settings.php` key or the `drupal_ai` provider never triggers a behind-the-scenes refresh, and budget-exhaustion is excluded. `HealthController` hands the same `cache.default` backend to `HealthChecker`, so a recorded failure surfaces as `ai_usable: false` / `ai_auth_failing: true` (status `degraded`). Built on scolta-php 1.0.5. Covered by `KeyExpiryRecoveryWiringTest`.
- **Re-sync `js/scolta.js` and `css/scolta.css` from canonical scolta-php (AI-Overview stall fix + drift since #205).** Headline (scolta-php#217): the sub-word frequency guard computed its corpus denominator with a match-all `pagefind.search(null)`, which downloads the **entire word index** — 5,678 chunks / 111 MB on the 6,909-page Wikipedia demo — and the AI summary is sequenced behind it, so the production AI Overview stalled 56–138+ s while the summarize endpoint answers in ~5 s (plausibly the Jun 5 Datadog "very slow to load/search" alerts). The denominator now comes from init-time cached totals (`pagefind-entry.json` page counts, `pagefind.filters()` value counts) and the guard never touches the word index. The byte-identical re-sync also carries the previously-unsynced scolta-php main changes since the last sync: the LLM filter-hint recall guard with offered chips (scolta-php#213 — `css/scolta.css` gains the offered-chip styles the synced JS references), the unmatched-subject sort fallback (scolta-php#210), and the PER-CS/renderer-parity cleanups (scolta-php#205/#206). No Drupal-side logic changed.

### Changed
- **Consolidated fragment-file enumeration into `IndexLocator::fragmentFiles()` (removed the duplicate glob in the health controller).** `HealthController` re-globbed `$location['fragmentDir'] . '/*'` byte-for-byte identically to the glob inside `IndexLocator::countFragments()`. The glob now lives in one new `IndexLocator::fragmentFiles()` method; `countFragments()` returns its count and `HealthController` consumes both the count and the file list (for its first-fragment integrity `filesize()` check). Behavior-preserving — same pattern, same `?: []` fallback. A unit test pins `count(fragmentFiles(loc)) === countFragments(loc)`.
- **The health endpoint now returns status-only without `administer scolta`.** `GET /api/scolta/v1/health` was gated by `use scolta ai`, which the module grants to the anonymous role at install — so the full diagnostic payload (AI provider, configured flags, index integrity, fragment counts, last-build time) was effectively public. Monitoring endpoints keep working; the detail moved behind admin: the route is now reachable without any permission (`_access: TRUE`, so uptime monitors work even on sites that revoked `use scolta ai` from anonymous) and answers `{"status": "ok"|"degraded"}` with HTTP 200, while the full payload requires the existing `administer scolta` permission. The full report is still computed before trimming, so the anonymous status continues to reflect index-integrity degradation. Health remains outside the AI-endpoint flood limits. Matches the status-only anonymous shape of the WordPress, Laravel, and Django adapters. Covered by `HealthPayloadTrimTest`.

### Security
- **Flood control on the anonymous AI API endpoints.** The three `/api/scolta/v1/*` routes are anonymous-by-default, cost-bearing LLM calls and had no rate limiting. The shared controller pipeline now checks per-IP and site-wide thresholds via Drupal's `flood` service before any AI work happens, failing closed with HTTP 429 (a flood-backend failure denies rather than bypasses). Thresholds are config-exposed (new `flood.*` keys with schema, install/example defaults — 60/min per IP, 1000/min site-wide, 0 disables a layer) and editable in a new "Rate Limiting" settings-form section. Functional tests cover the per-IP 429, the global 429, and the 0-disables case.
- **CSRF protection and open-redirect hardening on the dismiss-notice route.** `scolta.dismiss_rebuild_notice` was a state-changing GET with no `_csrf_token` requirement, and its `?destination` check (`str_starts_with($destination, '/')`) passed protocol-relative URLs, so `?destination=//evil.com` redirected off-site. The route now requires a CSRF token (the rendered Dismiss link carries it automatically), protocol-relative destinations are rejected, and the redirect goes through `Url::fromUserInput()` + `LocalRedirectResponse`. Functional tests cover the missing-token 403 and the `//evil.com` bypass; the dismissal-flow tests now click the rendered (tokenized) link.
- **Admin "Rebuild Index" no longer hand-rolls a shell command.** `ScoltaSettingsForm::rebuildWithBinary()` built a command string and `exec()`d it while the injected `PagefindBuilder` (binary allowlist, Symfony Process, 5-minute timeout) sat unused. The form now routes the binary build through `PagefindBuilder::build()`.

### Fixed
- **Baselined runtime fatal in the cron rebuild worker.** `ScoltaRebuildWorker`'s fingerprint-write error path called `$this->getLogger()`, which `QueueWorkerBase` does not have — the error path itself fataled, and the "Call to an undefined method" PHPStan error had been baselined instead of fixed. The fingerprint-write path (with its undefined-method error branch) is removed entirely: the worker now implements `ContainerFactoryPluginInterface` with all dependencies injected (lock, config, file system, stream wrappers, entity type manager, state, cache-tags invalidator, logger) and streams through `IndexBuildOrchestrator`, which owns change detection via its timestamp manifest — so the worker no longer computes or writes a separate change-detection fingerprint. The baseline entry is gone. Unit tests pin that the worker source carries no `getLogger(` or `computeFingerprint(` call and assert the debounce suspend-queue behavior.
- **Status report read a non-existent config key for the Pagefind binary.** `hook_requirements()` read `pagefind_binary`; the actual key is `pagefind.binary` (see `config/install/scolta.settings.yml`), so a configured binary path was always ignored in the status-report check.
- **AI provider misreported when the Drupal AI module is merely installed.** `HealthController` and `drush scolta:status` reported "Drupal AI module" based on module presence alone; routing actually requires the configured provider to be `drupal_ai` (same bug class as #125, which fixed the settings form but missed these two). Both now condition on the configured provider; `scolta:status` distinguishes "drupal_ai selected but module not installed".
- **`drush scolta:clear-cache` wiped the entire shared `cache.default` bin.** `$this->cache->deleteAll()` deleted every module's entries sitewide. The command now bumps the `scolta.generation` counter (AI expansion/summary cache keys embed the generation, so all existing entries are orphaned) and deletes the three fixed resolved-prompt keys. Behavior tests prove a generation bump invalidates cached AI entries while foreign cache entries survive.
- **Search-API-triggered binary rebuilds served stale AI caches for up to 30 days.** `ScoltaBackend::triggerRebuild()`'s binary path invalidated the tag `scolta:expand` — a no-op, since `DrupalCacheDriver` sets entries with no tags — and never bumped `scolta.generation`. The success path now bumps the generation and invalidates `scolta_search_index`; the dead tag invalidation is deleted.
- **Config schema used unsupported `mapping: {'*': …}` wildcards.** `sortable_field_descriptions`, `filter_field_descriptions`, and both `field_mappings` maps are arbitrary-key maps and are now `type: sequence`. Added the missing `auto_rebuild_delay` key to the `search_api.backend.plugin.scolta_pagefind` schema (the backend form clamps and saves it, but it had no schema).
- **Settings form silently discarded invalid input.** Malformed custom recency-curve JSON was wiped by `json_decode(...) ?: []` on save, and `parseKeyValueLines()` dropped pipe-less lines without feedback. Both now produce `validateForm()` errors naming the offending line. Functional tests cover both rejections and a subsequent valid save.
- **settings.php `$config['scolta.settings']` overrides did not apply to AI traffic.** `ScoltaAiService::buildConfig()` read `$config->getRawData()`, bypassing configuration overrides — the standard way to keep keys out of exported config. It now reads via `->get()`. A functional test asserts an override reaches the built `ScoltaConfig`.
- **Search block cache metadata and i18n.** The block's output varies by the `administer scolta` permission and by content language but declared neither `user.permissions` nor `languages:language_content` cache contexts, and used the site name without the `config:system.site` cache tag. The admin "index not built" notice and "Powered by Scolta" attribution were untranslated; the notice hardcoded `/admin/config/search/scolta` (now `Url::fromRoute('scolta.settings')`). Same hardcoded-path fix for `/admin/config/ai/providers` in the settings form (`Url::fromUserInput()`, works in subdirectory installs) and for the Amazee settings path in `BudgetExceededHandler` (`Url::fromRoute('scolta.settings.amazee')`).
- **Synced `js/scolta.js` from scolta-php — four shared browser-render bug fixes ([tag1consulting/scolta-php#199](https://github.com/tag1consulting/scolta-php/pull/199)).** Asset-only re-sync of the canonical browser script; no Drupal-side logic changed. (1) **Zero-result blank panel:** a search that returned no matches blanked the result panel for the entire duration of the asynchronous AI query-expansion round-trip — `renderResults()` cleared the container and header and returned early while expansion was in flight, so "No results found." only appeared after the expand promise settled (on a slow expand endpoint, a multi-second blank). It now shows a neutral "Searching…" in-progress state while expansion runs, then the terminal results-or-"No results found." once it settles. (2) **"1 results":** the header now pluralizes the noun on the count (`1 result` vs `N results`). (3) **Doubled quotes:** a quoted-phrase query rendered as `""merge conflict""` because the header wraps the query in its own quotes and `escapeHtml()` does not escape `"`; a matched surrounding quote pair is now stripped before the template re-adds one. (4) **Citation duplication:** AI-summary context (`buildLLMContext`) now collapses results that resolve to the same URL, so the summarizer is no longer handed — and no longer cites — duplicate sources. This resync also carries scolta-php main's previously-unsynced facet-count fix (`computeUnionFacetCounts`): facet counts no longer read all-zero on a long conversational query whose strict-AND search is empty — counts follow the same per-term OR union the result list uses. The committed copy is byte-identical to scolta-php's canonical `assets/js/scolta.js`; CI's asset-drift check compares against scolta-php `dev-main`, so it passes once scolta-php#199 merges to main.

### Changed
- **The four divergent content pipelines are unified through `ScoltaContentGatherer`.** The body-extraction + `ContentItem` construction block was duplicated in the admin "Rebuild Index" button (`ScoltaSettingsForm`), the Batch API step (`ScoltaBatchOperations::loadAndProcessChunk()`), and the cron queue worker — and only the gatherer (the documented single source of truth) handled translations, text-format rendering (`->processed`), `field_mappings`, and `hook_scolta_content_item_alter()`. Those three paths emitted raw unfiltered `->value` and skipped all of it, building a DIFFERENT index than `drush scolta:build` in violation of `scolta.api.php`'s contract. The per-entity conversion now lives in one private `buildContentItems()` pipeline; the batch path consumes the new `gatherByIds()` (ID slices, loaded 10 at a time), and the form's binary path streams `gather()`. A pipeline-parity functional test pins the contract: a node with a non-default text format, a translation, and a field mapping comes out identically from `gather()` and `gatherByIds()`, the queue-built index contains one fragment per gathered page (translations included), and filtered markup never reaches the index.
- **The cron queue worker runs the same streamed pipeline as `drush scolta:build`, debounced.** `ScoltaRebuildWorker` eager-loaded every published node (`loadMultiple()` on the full ID set — the exact memory blowup the 10-entities-per-load streaming gatherer was built to avoid, with auto_rebuild defaulting on). It now streams `ScoltaContentGatherer::gather()` (with the timestamp manifest, so unchanged entities skip full loads) through `ContentExporter::filterItems()` into `IndexBuildOrchestrator`, honoring the configured memory budget. It also consumes the two previously dead ends: the form-exposed-but-read-by-nothing `auto_rebuild_delay` backend setting and the written-but-never-read `scolta.rebuild_requested_at` state now implement a real debounce (the queue suspends until the delay has elapsed since the last content change, so an edit burst produces one build), and after a successful build the remaining duplicate queue items are drained.
- **One shared "index exists" resolver.** `PagefindBuilder::getStatus()` checked the legacy root `pagefind.js`, `HealthController` and `drush scolta:status` checked `pagefind/pagefind.js`, and the search block checked `pagefind-entry.json` — the same directory could be "built" in one report and "missing" in another. All four now resolve through the new `scolta.index_locator` service (`IndexLocator`: modern `pagefind/` layout first, legacy root fallback; `pagefind.js` is the load-bearing artifact). Upstreaming into scolta-php's `HealthChecker` is the eventual home.
- **AI controller triplication extracted into `AiApiControllerBase`.** `ExpandQueryController` / `SummarizeController` / `FollowUpController` were ~95% identical (constructor, `create()`, cache/generation/enricher resolution, JSON decode, error shape). The base now owns the whole request flow — flood check → `parseJsonBody()` (the new scolta-php shared decoder; controllers no longer hand-roll `json_decode` + 400 blocks) → one abstract `invokeHandler()` → shared success/error/limit response mapping. Plain string fields fall back to `->value`. Fixes comparison article excerpts showing `json {"body":"..."}` wrapper text in search results.

## [0.3.2] - 2026-04-24

Coordinated release. Ports the streaming gather and CLI wiring pattern from scolta-wp to Drupal.

### Fixed
- **Silent CLI during large builds**: `buildWithPhpIndexer()` was passing neither a logger nor a progress reporter to `IndexBuildOrchestrator::build()`. Added `DrushProgressReporter` (wraps Symfony `ProgressBar` via Drush's output interface) and now passes `$this->logger()` (Drush's built-in PSR-3 logger) to `build()`. (#7)
- **Peak RAM on large corpora**: `ScoltaContentGatherer::gather()` converted from a fully-materialized `ContentItem[]` (loading all entity IDs then `loadMultiple()` on all of them) to a `\Generator` that paginates with `->range()` in batches of 50 and calls `$storage->resetCache()` after each batch. The old code held all entity field data in RAM simultaneously; the new code holds at most one batch. (#7)
- **Lint**: Removed unused `MemoryBudgetConfig` import in `ScoltaCommands.php`. Fixed alignment, missing use statement, and missing `@return` description in `MemoryBudgetSettingsFieldSet.php`. (#7)

### Added
- **Flexible memory budget and chunk size**: `drush scolta:build` now accepts `--memory-budget=<budget>` with profile names *or* raw byte values (`256M`, `1G`), and a new `--chunk-size=<n>` flag to set pages-per-chunk independently of the memory profile. Both values are persisted as admin settings (`memory_budget.profile` and `memory_budget.chunk_size`). The settings form Memory Budget field is now a text input (with datalist suggestions) and a new Chunk Size number field has been added. Config schema and install defaults updated.
- **`ScoltaContentGatherer::gatherCount(string $entityType, string $bundle): int`**: COUNT-only entity query. Used by `buildWithPhpIndexer()` for early-exit and `BuildIntent` sizing without loading entity field data. (#7)

## [0.2.0] - 2026-04-13

### Fixed

- **UX:** `hook_requirements()` added to `scolta.install` — shows a warning in the Drupal Status Report when the Pagefind binary is not installed and the PHP fallback indexer is active, with instructions to install the binary for full language support.

### Added

- **Install hook**: `hook_install()` queues an initial index build on install and displays a status message with instructions for immediate building via Drush.
- **Index-missing validation in search block**: `ScoltaSearchBlock::build()` checks for the Pagefind index on disk; admins see a warning with a link to build, non-admins see nothing until the index is ready.
- **Rebuild Index button**: Admin settings form at `/admin/config/search/scolta` now includes a "Rebuild Index" button that triggers an immediate index rebuild using Batch API (PHP indexer) or synchronous binary execution.
- **Batch API integration**: PHP indexer rebuilds from the admin UI use Drupal's Batch API (`ScoltaBatchOperations`) to process content in chunks, preventing timeouts on large sites.
- **Queue Worker for auto-rebuild**: New `ScoltaRebuildWorker` queue worker (`scolta_rebuild` queue) processes index rebuild requests during cron, with a lock to prevent concurrent builds.
- **Auto-rebuild on entity changes**: `hook_entity_insert()` and `hook_entity_update()` automatically enqueue a rebuild when nodes are saved and `pagefind.auto_rebuild` is enabled.
- **Uninstall cleanup**: `hook_uninstall()` cleans up the rebuild queue, build lock, and state entries when the module is uninstalled.
- **PHP indexer integration**: `scolta:build` now supports in-memory PHP indexing via `Tag1\Scolta\Index\PhpIndexer`, eliminating the need for the Pagefind binary.
- `--indexer` option on `scolta:build` to select indexer mode (`php`, `binary`, or `auto`); overrides the `indexer` config setting.
- `--force` option on `scolta:build` to skip the content fingerprint check and force a rebuild.
- `indexer` config key (`auto`/`php`/`binary`) in `scolta.settings.yml` with matching schema entry.
- Auto-detection: when `indexer` is `auto`, the build command uses the binary if available, otherwise falls back to the PHP indexer.
- Content fingerprint tracking (`.scolta-state` file) to skip unnecessary rebuilds when content has not changed.
- `wasmPath` key added to `drupalSettings.scolta` in `ScoltaSearchBlock`, pointing to the WASM glue JS file served from the module directory.
- `ai_languages` config setting for multilingual AI response support, configurable via the admin form (comma-separated language codes)
- All AI controllers now pass `aiLanguages` from config to `AiEndpointHandler`
- `PromptEnrichEvent` Symfony event dispatched before AI prompts are sent to the LLM provider
- `EventDrivenEnricher` bridging scolta-php's `PromptEnricherInterface` with Drupal's event system
- All AI controllers now inject the event dispatcher and pass the enricher to `AiEndpointHandler`

### Removed

- **Extism/FFI dependency**: All references to `ScoltaWasm`, `ExtismCheck`, `Tag1\Scolta\Wasm`, FFI, and Extism have been removed. scolta-php is now pure PHP with no native extensions required.
- FFI extension removed from CI workflow (`setup-php` no longer requests `ffi`).
- `continue-on-error` removed from CI lint step so lint failures are caught.
- `testScoltaPhpWasmPathUsesUnderscores` test removed (ScoltaWasm.php no longer exists in scolta-php).
- `isExtismAvailable()` helper and associated skip logic removed from `ScoltaSettingsFormTest` since `toJsScoringConfig()` is now pure PHP.

### Changed

- **Client-side WASM scoring**: Scoring, merging, and query expansion parsing now happen entirely in the browser via WASM instead of server-side PHP/WASM. The `wasmPath` setting is injected into `drupalSettings` so `scolta.js` can load the WASM glue module.
- WASM assets (`scolta_core.js`, `scolta_core_bg.wasm`) are now copied to `js/wasm/` by the `copy-assets` composer script alongside the existing JS/CSS assets.
- `scolta:build` Drush command now pre-resolves and caches all prompt templates (Step 3) after building the Pagefind index, reducing runtime overhead for API endpoints.
- Prompt resolution uses pure PHP (`DefaultPrompts::resolve()`) instead of WASM calls.
- Updated PHPDoc comments to remove stale references to WASM/FFI/Extism.

### Previously added

- Search API backend (`ScoltaBackend`) for Pagefind-based indexing and search
- 7 Drush commands: `scolta:build`, `scolta:export`, `scolta:rebuild-index`, `scolta:status`, `scolta:clear-cache`, `scolta:download-pagefind`, `scolta:check-setup`
- Admin settings form at `/admin/config/search/scolta` with AI, scoring, display, cache, and prompt configuration
- Search block (`ScoltaSearchBlock`) for placing the search UI in block regions
- 4 API endpoints: `expand-query`, `summarize`, `followup`, `health` at `/api/scolta/v1/`
- `DrupalCacheDriver` implementing `CacheDriverInterface` for Drupal's cache API
- Content export pipeline integrating Search API indexing with Pagefind HTML generation
- Drupal permissions: "Administer Scolta" and "Use Scolta AI features"
- Config schema and install defaults in `config/schema/` and `config/install/`
- Symlinked shared assets from scolta-php (`scolta.js`, `scolta.css`)
- Drupal behavior bridge (`scolta-drupal-bridge.js`) for Drupal.behaviors integration
