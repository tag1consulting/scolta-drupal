# Changelog

All notable changes to scolta-drupal will be documented in this file.

This project uses [Semantic Versioning](https://semver.org/). Each Scolta package versions independently; compatibility with scolta-php is expressed by the caret constraint in `composer.json` rather than by matching version numbers.

## [Unreleased]

### Changed
- **The browser bundle deploys from the installed scolta-php instead of being committed here (`src/Service/AssetDeployer.php`, `scolta.install`, `scolta.module`, `scolta.libraries.yml`, `src/Plugin/Block/ScoltaSearchBlock.php`).** `js/scolta.js`, `css/scolta.css` and the WASM pair were committed copies of `scolta-php/assets/`, kept honest by a manual `composer copy-assets` re-vendor step and the `assets-in-sync` CI byte-comparison — a whole apparatus whose only job was compensating for `hook_install()` running once per site ever: the install hook already copied from vendor, but an updating site never re-ran it, so the committed file was the one thing keeping updates current. The bundle now deploys to `public://scolta-assets` — writable on every host, including immutable-code deploys where the module directory is not — at install, in update hook `scolta_update_10005()`, and on **every cache rebuild** via `hook_rebuild()`, which is the piece that makes `composer update` + `drush cr` sufficient to ship a new bundle with no module release and no re-vendor commit. The deployer compares each file against the vendored canonical (size, then hash — never a version recorded in state, so a wiped or hand-edited files directory self-heals) and copies only what differs, so the no-change rebuild costs a few stat calls and an unchanged file keeps its mtime for CDN/rsync-style deploys. Each copy lands via temp-file-plus-rename, so a client fetching mid-deploy — or a rebuild killed mid-copy — never sees a truncated file at the served path. `scolta.libraries.yml` references the deployed copies by stream-wrapper URI, which library definitions support natively, and the block resolves `wasmPath` the same way, dropping its `ModuleExtensionList` injection. Removed with the committed copies: the `copy-assets` composer script, the `assets-in-sync` CI job (**take it off the required-checks list**, as a required check that never reports blocks every merge), and the coordinated-change dance where this repo's `main` sat red until a matching scolta-php PR merged. Tests that asserted the committed copies now assert the replacement invariants: nothing may commit a bundle file (`StructuralIntegrityTest`), the library must point at `public://scolta-assets` and the rebuild/install deploys must exist, and a new `AssetDeploymentFunctionalTest` proves on a real install that deployment is byte-identical, that `drupal_flush_all_caches()` repairs a stale copy — including a same-size corruption — and that uninstall removes the directory. Tests that read the bundle's *content* (`SaytSettingsTest`, `LayoutCssRegressionTest`, `BrowserConfigParityFunctionalTest`, the Playwright layout specs) read the vendored canonical, the same bytes a site serves. The dist tarball shrinks by ~1.5 MB and its validator's size cap drops to match; `UPGRADE.md` carries the operator-facing note (run `drush updb`/`drush cr` after updating, and update anything that hardcoded the old `modules/.../scolta/js/` paths).

## [1.3.0] - 2026-08-19

### Fixed
- **Search API's "Manage fields" form no longer fatals (`scolta.module`, `tests/src/SearchApiFieldsHelpTextTest.php`).** `scolta_form_search_api_index_fields_alter()` called `$index->getServer()`, which `IndexInterface` does not define, so the form raised `Error: Call to undefined method` — for every index on the site, not only Scolta-backed ones, and the hook's `catch (\Exception)` does not catch an `Error`. It now calls `getServerInstance()`, whose contract the surrounding code already assumed: NULL when the index has no server, `SearchApiException` when the server cannot be loaded. The test that guarded this asserted the source contained `getServer()`, so it pinned the broken call rather than the working one; it now checks the accessor that exists. Found by `ddev phpstan`, where mglaman/phpstan-drupal can resolve search_api classes that the isolated CI run cannot.
- **Injected services on `AmazeeSettingsForm` and `ScoltaSearchBlock` survive serialization (`src/Form/AmazeeSettingsForm.php`, `src/Plugin/Block/ScoltaSearchBlock.php`).** All twelve were promoted `private readonly`. `FormBase` and `BlockBase` both carry `DependencySerializationTrait`, which restores a cached form or plugin by reassigning its service properties — an assignment that cannot reach a private property and cannot write a readonly one at all, so restoring either object raised "Cannot modify readonly property". They are now `protected` and mutable, with a comment on each constructor saying why. See https://www.drupal.org/node/3110266.
- **`drush scolta:build --force` no longer costs the next build a second full gather (`src/Service/ScoltaContentGatherer.php`, `src/Commands/ScoltaCommands.php`).** `--force` means "reload every entity, trust nothing cached", and it was implemented by withholding the timestamp manifest from the gatherer entirely. Withholding it also stopped the build writing to it: `put()` is what marks an entity seen, `pruneAndSave()` deletes whatever was not seen, and the orchestrator runs that prune at the end of every build against its own manifest instance. So a forced build emptied the manifest it had just declined to read. The forced build itself looked correct, and the cost landed on the next one, which found nothing to be incremental against, treated the whole corpus as changed and ran a second full gather — on a production-sized corpus a ~55m cold build where a ~10m warm one was expected, with nothing in either build's output to explain it. The gatherer now gates only the **skip decision** on `--force`, and records every entity it loads regardless, so a forced build leaves the manifest primed rather than empty. **The timestamp query moved out of the gate with it**, which is the part that is not obvious: `getEntityTimestamps()` supplies the value that gets *stored*, not merely the input to the skip decision. Left gated, a forced build stores nothing from it and `$entityTs` falls through to `buildContentItems()`, which reads the changed time off the first translation carrying a body — a different value from the query's on any multilingual entity, so the entry the forced build wrote would never match on the next build and the corpus would re-gather forever. One extra `SELECT` per 200-ID page is nothing beside loading every entity, which is what `--force` already is. `gatherByIds()` carried the same three gates and gets the same treatment.
- **The exporter can now record the bodies it drops, so they stop being re-gathered every build (`src/Commands/ScoltaCommands.php`, `src/Plugin/QueueWorker/ScoltaRebuildWorker.php`).** The gatherer filters on changed timestamps and never sees a body, so it records every entity it loads — including the ones `ContentExporter::filterItems()` immediately drops for cleaning down to less text than the minimum worth indexing. Those returned on the next build as cached references whose token lookup could only miss, and each miss pruned the entry and re-gathered the entity so it could be dropped again: on a 109k-page corpus, 13,678 documents re-gathered on every warm build, indefinitely, under a `warning` that read like data loss. scolta-php records the dropped hash when `filterItems()` is given the build's manifest; both build paths now pass it, and both pass the **same instance** the gatherer and orchestrator use, since two instances would each hold half the state and prune the other's away. Requires the recorder in scolta-php; against a release without it the argument is accepted and ignored, so this module is correct either way.

### Added
- **`--entity-ids` option on `drush scolta:build` (`src/Commands/ScoltaCommands.php`, `README.md`).** Takes a comma-delimited list of entity IDs and scopes the build to exactly those entities, the way `--bundle` scopes it to a bundle: the published index contains only them. IDs that cannot be loaded — malformed, nonexistent, or unpublished — are reported in one notice and skipped rather than silently shrinking the index. The IDs stream through the same `gatherByIds()` pipeline the queue worker uses, so translations, text-format rendering, field mappings, and `hook_scolta_content_item_alter()` all apply, and the resume chain passes the list through to its segments. `--bundle` is ignored, since the list already names the exact entities. PHP indexer only; an explicit `--indexer=binary` with `--entity-ids` errors instead of ignoring the option.
- ** Add a .ddev directory for local development.** Uses the https://github.com/ddev/ddev-drupal-contrib/ add-on.
- **"Facet index loading" setting, controlling when the browser downloads the facet index or whether it downloads it at all (`src/Form/ScoltaSettingsForm.php`, `src/Plugin/Block/ScoltaSearchBlock.php`, `config/install/scolta.settings.yml`, `config/schema/scolta.schema.yml`).** Three modes under Display, defaulting to `eager`, which is the behaviour every existing site already has. `eager` downloads the index with the search page, so the filter sidebar is populated before the first results paint. `deferred` skips that download and takes it the first time a visitor uses a filter: on a large site the index runs to a megabyte or more, and a theme that renders its own facets was paying for it on every search-page load to display nothing from it, in sessions that mostly never filter at all. Scolta's own filter sidebar stays empty until that first interaction under `deferred`, because it is built from the index. `disabled` never downloads it, renders no filter sidebar, runs no facet filtering, and skips the per-query facet count pass. Deferring does **not** degrade filtering: the bundle finishes the load before applying the selection, so it never falls back to Pagefind's own per-search filtering, which would cost every later search on the page. The value is read from Drupal config rather than from `ScoltaConfig`, matching how the SAYT keys are passed, so the setting works against any scolta-php in the supported range; an unrecognized value clamps to `eager` in the form, in the block and in the bundle.
- **`scolta.ai_access`, one decision point for who may use the three AI features (`src/Access/AiAccessInterface.php`, `src/Access/AiAccess.php`, `src/Access/AiFeatureAccessCheck.php`, `scolta.services.yml`, `scolta.routing.yml`, `README.md`).** A site whose rule is narrower than "this role may" had nowhere to put it: `use scolta ai` is a role permission, and the only other input — the `ai_expand_query` / `ai_summarize` flags — is site-wide config. A per-user preference, a quota, or an entitlement carried on a subscription could be enforced on the endpoints by a route subscriber, and separately in the browser by rewriting `drupalSettings` from `hook_js_settings_alter()`, with nothing keeping the two in step. `AiAccessInterface::access($account, $feature)` now answers once for both call paths and returns an `AccessResultInterface`, so the answer carries its own cacheability. The shipped `AiAccess` states the existing rule and no more — `use scolta ai`, with an unrecognised feature name refused rather than allowed — so on a site that has decorated nothing the new requirement answers exactly what `_permission` already answered. **The config flags are deliberately not part of it:** `ai_expand_query`, `ai_summarize` and `max_follow_ups` say what the site offers rather than who may ask, `AiEndpointHandler` already enforces all three with the status codes callers are written against (404 for a switched-off feature, 429 carrying the remaining `limit` for the follow-up quota), and restating them here would turn those documented responses into a bare 403 from routing. The quota could not be expressed as access in any case, since the real rule counts the messages in the request body, which no access check sees. `ScoltaSearchBlock` combines the two itself: config decides whether a feature is offered at all, this service decides whether the visitor gets it. Sites decorate the service; `README.md` has the recipe, including the part that bites — an implementation varying by account must say so on the result it returns, because the block's render array takes that cacheability on, and should say it with a cache context keyed on the value the rule reads rather than `cachePerUser()`, which would cost a cache variant per account where a boolean preference needs two. The AI routes keep `_permission: 'use scolta ai'` and gain `_scolta_ai: <feature>`, checked by `AiFeatureAccessCheck`: Drupal requires every requirement to allow, so the permission still refuses on its own and no site that has not decorated anything sees a different answer than before.

### Changed
- **Raised the `tag1/scolta-php` floor to `^1.3.0` (`composer.json`, `composer.lock`).** This release opens the 1.3.0 line, and the lock now names the released scolta-php 1.3.0 rather than a development version, which is what `lock-guard` checks at tag time.
- **The AI review runs on pull requests from forks, so an outside contribution is no longer red for being outside (`.github/workflows/ai-pr-review.yml`).** The `review` job was triggered by `pull_request`, and GitHub withholds repository secrets from a fork's `pull_request` run: the API key arrived empty and the action exited 1 on `ANTHROPIC_API_KEY is required for AI_PROVIDER=anthropic`. It also downgrades `GITHUB_TOKEN` to read only on that event, so a key would not have been enough; there was no path by which the job could post a review. The result was a check that could only be red on a fork PR and only green on ours, and it failed at the container's first step, before reading a line of the diff, so it was never a statement about the contributed code. Both open outside contributions ([#214](https://github.com/tag1consulting/scolta-drupal/pull/214), [#217](https://github.com/tag1consulting/scolta-drupal/pull/217)) sat red on it while the sixteen jobs that do validate the code, the three PHP matrix runs, `functional`, `playwright`, `phpstan`, `assets-in-sync` and the rest, passed on both: they need no secret beyond the read scoped `GITHUB_TOKEN` composer already gets. The trigger is now `pull_request_target`, which runs this file from `main` with base repository secrets in scope, so fork and internal pull requests are reviewed on the same terms. Dependabot pull requests, which GitHub withholds the same secrets from, are covered by the same change. **What makes that safe is an invariant of the action rather than of this workflow**: `ai-pr-review` treats the checked out tree as data and never as code, running no build, install or test step against the PR head and invoking its bundled analyzers on repository content, an invariant its `SECURITY.md` states and `tests/python/test_security_canary.py` guards on every one of its own pull requests. The hardening that belongs on this side is here: the checkout pins `github.event.pull_request.head.sha` rather than a ref, which cannot move underneath the review the way a ref can when a fork pushes between the event and the checkout; `persist-credentials: false` keeps the base repository token out of a working tree full of fork authored files; the `release/` branch heuristic that selects the expensive full review mode is now gated on the pull request originating in this repository, since `head.ref` is a string the fork chooses and releases are not cut from forks; and a concurrency group supersedes an in flight review instead of letting a rapid series of pushes stack up billable runs. The upstream template's hardened variant also restores `container-action/` from the base SHA, which is **deliberately not copied**: that step belongs to the action's own repository, which vendors that directory, while this workflow names `tag1consulting/ai-pr-review/container-action@main` and Actions resolves it from the action repository rather than from this checkout, so the step would have nothing to restore and would fail on the missing pathspec. Nothing about the merge gate changes, because `review` was never in this repository's required checks list; what changes is that an outside contributor now gets the review rather than a failure notice, and their code stops being the only code here that nothing reviews.
- **The fork review actually reaches the diff: `actions/checkout` needs an explicit opt-in to place fork code in a `pull_request_target` workspace (`.github/workflows/ai-pr-review.yml`).** The entry above switched the trigger and was verified on internal pull requests, where nothing about fork handling runs. On the first real fork event the checkout refused before the action started: "Refusing to check out fork pull request code from a `pull_request_target` workflow", pointing at `allow-unsafe-pr-checkout`. The input was visible all along, printed as `allow-unsafe-pr-checkout: false` in the checkout step of every earlier run, and the upstream template's fork instructions do not mention it because that project dogfoods on branches of its own repository, where the gate does not apply. The opt-in is set here, with the reasoning beside it rather than left implicit: the gate exists because fork code executed with base repository secrets in scope is the "pwn request" shape, and nothing in this job executes what it checks out. The only consumer of the working tree is the action, which commits to treating it as data and never as code. The line carries the condition of its own removal, that any step added to this job which runs something out of the workspace takes it with it. **A second fork-only behaviour is documented in the same change and cannot be fixed from this side**: `pull_request` reads the workflow file from the *PR branch*, so a pull request opened before the trigger changed still fires a secretless `pull_request` run from its stale copy of this file alongside the `pull_request_target` run from `main`. Separate workflow runs produce separate check runs and do not supersede one another, so the stale failure sits beside the new result until the contributor's branch picks the change up; a merge or rebase on their branch leaves one check again.
- **Re-vendored the browser bundle from scolta-php `1.3.0` (`js/scolta.js`, `js/wasm/scolta_core.js`, `js/wasm/scolta_core_bg.wasm`).** `js/scolta.js` carries the `facetMode` implementation the setting above drives; the two WASM files carry the rebuilt scolta-core 1.0.2 engine, which decomposes a category query into the things it contains instead of restating the category, and redacts IPv6 addresses and unhyphenated SSNs in `sanitize_query`. `css/scolta.css` is unchanged.
- **Re-vendored the browser bundle again, carrying two later scolta-php changes (`js/scolta.js`).** Both are browser-side and neither needs anything from this module, so `js/scolta.js` is again the only one of the four vendored files that moves; `css/scolta.css` and both WASM assets stay byte-identical. **An empty search box now browses the corpus instead of painting nothing** ([scolta-php#288](https://github.com/tag1consulting/scolta-php/pull/288)): `doSearch()` opened with an early return when there was no query, so a visitor who selected a facet without typing got no response to the click at all, not an empty state, with whatever was last painted left on screen. Browse and search are now one path that differs only in whether a filter is applied. A browse has no relevance signal, so the listing comes back in Pagefind's default order rather than through the scorer; it has no query, so no expansion is requested, none is inherited from the search the visitor just left, the result-count header names no query and no `q` parameter is written. **Arriving at a search page with no `?q=` still renders nothing**, because the bootstrap only searches when that parameter is present, so this is reached by an explicit submit, a facet toggle or a sort. The `MAX_PAGEFIND_RESULTS` cap and `RESULTS_PER_PAGE` pagination apply unchanged, which is what keeps a browse of a large corpus costing what a query costs, and the filtering runs against the `scolta.facets` artifact rather than through a Pagefind filters object, so no `.pf_filter` chunk is fetched and later searches on the page are not taxed. **And function words are no longer highlighted in excerpts and titles** ([scolta-php#287](https://github.com/tag1consulting/scolta-php/pull/287)): the two secondary highlight paths, the empty-meaningful fallback and the AI expansion decomposition, were gated on `length > 2` and nothing else, which passes "and", "the", "for", "but", "with" and every other function word of three letters or more, so an expansion term such as "reading and writing" marked "and" in every excerpt and title on the page. Both now consult the same effective stopword set that query tokenization uses, custom stop words included. The primary meaningful-terms path was always clean and is untouched. Copied with `composer copy-assets`; because `assets-in-sync` byte-compares the committed copies against scolta-php `dev-main` on every run, this repository's `main` was red from the moment those two merged upstream until this landed, with no change of its own to explain it.
- **Removed the `version-sync` CI job (`.github/workflows/ci.yml`, `CLAUDE.md`).** The job failed unless the major version in `scolta.info.yml` equalled the major in this module's `tag1/scolta-php` constraint, which is a lockstep-release rule rather than a compatibility check: a scolta-php 2.0 would have obliged a scolta-drupal 2.0 whether or not anything in this module changed, and a scolta-drupal 2.0 could not have shipped against a supported 1.x library. The constraint already states which scolta-php releases this module runs against and Composer enforces it on every install, so the job restated that in version numbers and added a release obligation nothing here needs. Raised in review of [#221](https://github.com/tag1consulting/scolta-drupal/pull/221). **The version checks that survive are the ones the constraint cannot express**: `version-consistency` hard-fails on a `version` key in `composer.json`, because the drupal.org Composer facade honours a declared version and a site tracking a dev branch could then `composer update` but never `composer install`; `assets-in-sync` byte-compares the committed `js/`, `css/` and WASM files against scolta-php, because drupal.org ships the git tarball and Composer does not run a dependency's install scripts, so the committed blob is the file a site receives; `coherence` refuses a package that states two development lines about itself, which is self-consistency and not lockstep; and `release.yml`'s lock guard still refuses to publish a stable release whose lock names a development version, which is the one real cross-repository gate that remains. `version-sync` was a required status check on `main` and comes off the branch protection list with it, since a required check that never reports again blocks every merge. The versioning paragraph in `CLAUDE.md` and this file's header said major versions were synchronized across all Scolta packages, and now say what the CI does: each package versions independently, compatibility travels in the constraint. scolta-core's `VERSIONING.md`, which both defer to, is corrected separately.

### Fixed
- **The search UI no longer offers AI features to a visitor who cannot use them (`src/Plugin/Block/ScoltaSearchBlock.php`).** `build()` emitted `AI_EXPAND_QUERY` and `AI_SUMMARIZE` straight from site config for every visitor, having never looked at who was asking, while the endpoints behind both flags have required `use scolta ai` since 1.0. **On a default install that is precisely the anonymous case**, since 1.1.0 stopped granting the permission to the anonymous role: an anonymous visitor was handed the full AI search, fired expand and summarize on every query, and got a 403 from each — which `scolta.js` swallows into a `console.warn`, so the page showed no error and simply took longer to do less. Each flag is now the config value it always was **and** the answer `scolta.ai_access` gives for that account, so a switched-off feature is still not advertised and a visitor who cannot use one is no longer told it exists. The access result's cacheability is merged into the block's render array, so the shipped rule adds the `user.permissions` context and a decorator's own contexts and tags arrive with it. A site that grants the permission to anonymous sees no change.
- **Coverage (`tests/src/Functional/AiAccessFunctionalTest.php`, `tests/src/AiAccessWiringTest.php`).** The functional test drives a rendered page and the three endpoints together, so it asserts the property that was broken rather than either half of it: what the page claims and what the endpoint does agree, for a permitted visitor and for one without the permission. A third case pins what this change must *not* touch — a feature switched off in config still answers the handler's 404 rather than a 403 from routing — because an earlier revision of this branch folded the config flags into the access rule, which also broke `ScoltaExportFunctionalTest::testFollowUpLimitEnforced` (left to cover the quota, rather than restated here). The file-inspection test pins what the behavioural one cannot see going wrong on a site: that the access check keeps its `access_check` tag, since an untagged one makes `_scolta_ai` match nothing silently and with no error anywhere; that the block combines the config flag with the access answer rather than replacing it, and bubbles the result's cacheability; and that `AiAccess` reads none of the three config keys.

## [1.2.0] - 2026-08-07

### Added
- **`UPGRADE.md`, with the 1.2 upgrade notes (`UPGRADE.md`, `scripts/validate-dist-archive.sh`).** The `ScoltaContentGatherer::gather()` signature change was only a `### Fixed` bullet, which is the wrong shape for a break: parameter 4 went from `int $startPage` to `int|string|NULL $resumeFromId`, and PHP resolves a signature-compatibility violation when the subclass is **defined**, so a subclass or decorator still declaring the old signature is a fatal at class load on every request that autoloads it, whether or not anything calls `gather()`. No shim can precede a class-load failure, so the only thing that helps is telling the site owner. The file also points at scolta-php's 1.2 notes for the two breaks inherited through the vendored library. It ships in the distribution archive alongside `CHANGELOG.md` and `README.md`, so it is added to the fail-closed `ALLOWED_TOP_LEVEL` list in `validate-dist-archive.sh`.

### Changed
- **`tag1/scolta-php` is required as `^1.2.0`, and the committed lock names the release (`composer.json`, `composer.lock`).** The floor was `^1.2@dev`, which is what the entry below settled on while 1.2.0 did not exist: it refuses 1.1.0 and reaches the development branch from a root that asks for it. scolta-php 1.2.0 is now tagged and on Packagist, so the `@dev` suffix comes off exactly as that entry said it would, and the lock moves from `dev-main` to the 1.2.0 release resolved from Packagist. A published package no longer depends on a development constraint, and `release.yml`'s lock guard, which refuses to publish while the lock names a development version, is satisfied for the first time. The `extra.branch-alias.dev-main` entry moves from `1.1.x-dev` to `1.2.x-dev` in the same commit: a consumer resolving `dev-main` is aliased onto whatever line the alias names, so leaving it on 1.1 would have left `dev-main` unable to satisfy the `^1.2.0` this package now requires of itself.

### Fixed
- **Re-vendored the browser bundle (`js/scolta.js`) from scolta-php 1.2.0: facet counts stop reading high, and a facet value no visible result carries is no longer offered.** Two changes in the released bundle, both in the count path. The expansion delta is now collapsed exactly as the result list collapses it, through `mergeResults()` and then `deduplicateByTitle()`, **before** any value is counted, so a document the list folds away is no longer counted behind a row the user cannot reach; on a corpus with formulaic titles the panel read one high per collapsed pair. And `suppressUnreachableValues()` zeroes any value that no document in the ranked list carries, so a count is again a promise that clicking it produces results rather than a click through to "No results found". It stands down when the user has a facet selection active, where presence in the list is not a sound reachability test, and when a deployment's fragments carry no `filters` at all. Copied from `vendor/tag1/scolta-php/assets/` with `composer copy-assets` against the locked 1.2.0 release; `css/scolta.css` and both WASM assets were already byte-identical to 1.2.0 and are unchanged.

### Fixed
- **The declared floor for `tag1/scolta-php` refuses a release this module cannot run on (`composer.json`, `.github/workflows/ci.yml`, `tests/src/ScoltaPhpFloorTest.php`).** `composer.json` required `tag1/scolta-php` as `^1.1.0` while `src/AiProvider/Amazee/DrupalConfigStorage.php` declared `implements ProvenanceAwareConfigStorageInterface` and typed two methods to `AmazeeConnectionSource`. Neither symbol exists in the 1.1.0 release, and an `implements` clause is resolved when the class is defined rather than when a method is called, so `composer require tag1/scolta-drupal:dev-main` resolved scolta-php 1.1.0 and fatalled on the first request that touched the settings form. This repository is public, so anybody could reach that state. The previous plan, recorded below, was to hold the committed `composer.lock` at the stable release and bump it when 1.2.0 is tagged; a lock governs this repository's own installs and says nothing about what an integrator resolves. The constraint is now `^1.2@dev`, which refuses 1.1.0, reaches the development branch from a root that asks for it, and needs only the `@dev` suffix dropped once 1.2.0 exists. Settled against composer 2 with only a v1.1.0 tag present and main aliased to `1.2.x-dev`: `^1.1.0` resolves 1.1.0, `^1.2` fails because nothing stable satisfies it, `^1.2@dev` resolves `dev-main`, and `dev-main` resolves `dev-main`. **Nothing caught this because every CI job here overwrote the constraint with `dev-main@dev` before running composer**, so no job ever resolved the constraint this package ships. The `test` job no longer rewrites it, since `^1.2@dev` reaches the development branch on its own, and `ScoltaPhpFloorTest` asserts the shipped constraint cannot resolve 1.1.0 and that the two symbols it exists for are still loaded unguarded. The `class_exists()` guarded `IncrementalIndexUpdater` path is deliberately not part of the floor: it is dormant on an older library rather than fatal on it.
- **The committed lock follows the floor, and the stable-release rule moves to where it can be kept (`composer.json`, `composer.lock`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `CLAUDE.md`).** Raising the floor left `composer.lock` naming 1.1.0, and a lock that does not satisfy the constraint beside it is not a slow-burning inconsistency: `composer install` refuses outright, while every CI job here resolves with `composer update` and stays green. The lock now names `tag1/scolta-php dev-main` from Packagist. Regenerating it required one further change: the `../scolta-php` path repository is canonical by default, which meant it blocked Packagist entirely for that package and no lock resolved on a machine with the sibling checked out could ever be anything but `dist.type=path`. It is now `"canonical": false`, so the path repo supplies a local build when it is the best match and steps aside when it is not. ### Fixed
- **`drush scolta:build` owns the index it was asked to build, instead of exiting 0 while a detached chain decides (`src/Commands/ScoltaCommands.php`).** On a `memory_abort` the command ran `exec('drush scolta:build --resume … &')` and returned. The parent exited **0** having indexed nothing it could vouch for, its "Index built" success line never printed but its exit status saying otherwise, and roughly twenty linked background processes ran on for about eleven minutes with their output going to `/tmp/scolta-resume.log` and nobody reading it. Whatever that chain produced — including, on a 1,426-page corpus, an index of 1,150 fragments, and on a larger one an index whose posting lists pointed at the wrong documents — the operator and any deploy pipeline had already been told the build succeeded, because a zero exit status is the only thing a pipeline reads. Each detached segment inherited the same defect, so the failure compounded silently. `runResumeChain()` now drives the segments in the foreground with `proc_open`, streaming each one's output, and requires every segment to commit pages the previous one did not — a chain that stops progressing fails with the page count it stalled at rather than spawning until someone notices — bounded by `MAX_RESUME_SEGMENTS`. A process invoked with `--resume` is a segment and never starts a chain of its own, so exactly one bootstrapped Drupal is alive per build rather than one per segment. **Every failure path now throws**, so drush exits non-zero: a memory limit hit before any chunk committed, a stalled chain, an exhausted segment budget, a non-zero `scolta:finalize` (previously logged as an error and then followed by a success line). Success is reported only after `IndexBuildOrchestrator::verifyIndexComplete()` passes, and a chain reports the fragments actually on disk rather than the partial count belonging to whichever segment this process happened to run.
- **The resume offset no longer skips the wrong rows on a translated corpus (`src/Commands/ScoltaCommands.php`).** `--resume` passed the manifest's `pages_processed` to `ScoltaContentGatherer::gather()` as a starting entity offset. Those units are not the same: the manifest counts *pages*, the gatherer's cursor walks *entities*, and an entity yields one page per translation. On a 287-entity corpus that indexes as 1,426 pages, resuming after 1,150 pages asked the cursor to skip 1,150 entities out of 287, so it skipped past the end and the segment re-indexed the whole corpus — reported as "Index built: 2,576 pages" against 1,426 fragments on disk. On a monolingual corpus the two units coincide, the skip lands, and the resumed segment renumbers real pages instead, which is the worse half of the same bug. `gather()` now takes a resume boundary that is an entity ID, seeded from the highest entity the page-table ledger records this build as having committed and applied inclusively, because that entity may have had only some of its translations indexed before the limit hit; the orchestrator drops the ones it already has. Restarting the walk rather than re-reading matters at scale: re-reading made each segment load every entity up to its predecessor's stopping point, so progress *fell* segment over segment (200 pages, then 50) and a 6,944-entity corpus was on course to exhaust its segment budget. With the cursor it holds steady at ~350 pages per segment and the same corpus completes in 20.
- **The memory budget form no longer advertises a ceiling the code does not enforce (`src/Form/MemoryBudgetSettingsFieldSet.php`).** The profile selector offered "Conservative — ≤ 96 MB peak", which reads as a guarantee about process memory. It is not one: 96 MB is what Scolta budgets for its own work, and Drupal's ~130 MB baseline plus I/O overhead sits on top, so measured peaks were 137 MB on a 1,426-page corpus and far higher on a large one — an operator sizing a container from that label under-provisioned it and met the memory failures the profile was chosen to avoid. The options now say what the figure budgets, and the description states that total process memory adds the baseline, and that a profile larger than `memory_limit` is reduced to fit rather than allowed to fail mid-build.

### Added
- **An ordinary content edit now updates the index instead of rebuilding it (`scolta.module`, `src/Plugin/QueueWorker/ScoltaRebuildWorker.php`, `src/Service/ScoltaContentGatherer.php`, `config/install/scolta.settings.yml`, `config/schema/scolta.schema.yml`).**
  The queue item carried no identity of what changed: `_scolta_auto_rebuild_check()` had the saved entity in scope and enqueued `['type' => 'auto']`, discarding it. The worker therefore could not know that three nodes had changed rather than a hundred thousand, and its only available answer was to gather the whole corpus. That is not a merge cost that could be tuned away — on a 109,308-page corpus a warm build measured 2876.4s of which the content gather was **2433.3s, 84.6%** — so an edit cost a full build no matter how good the index writer got. The enqueue sites now carry the entity ID, the operation, and the per-translation content item IDs (`'42'`, `'42-es'`) the gatherer would produce, and those IDs are derived by the new `ScoltaContentGatherer::itemIdsFor()` rather than rebuilt at the call site, because the page-table ledger keys its ordinals by exactly those strings and a second copy of the rule would orphan pages the moment the two drifted. When a change set is small and an index with a ledger exists, the worker gathers just those IDs with `gatherByIds()`, stages each resulting `ContentItem` with `stageUpsert()`, stages removals with `stageDelete()`, and calls `commit()`. Nothing in the suite caught it because nothing tested a delete. The delete now enqueues the removed node's content item IDs, which the incremental path tombstones and the full build path prunes. - **Removing a translation removes its page (`scolta.module`).** A removed translation is gone from the saved entity's translation list, so a payload derived from the post-save entity alone never mentions its page ID: it is not staged as an upsert, so it is never *missing* from the gather either, so nothing removes it and **the orphaned translation stays searchable until an unrelated full rebuild**. ### Changed
- **The corpus walk fetches IDs in pages of 200 and still loads entities 10 at a time (`src/Service/ScoltaContentGatherer.php`).** The walk paged the entity query at the load batch size, so a 123,957-row corpus ran 12,397 queries costing **764.7s, 31.4% of the gather**. The expected culprit was `LIMIT n OFFSET m` going O(m), and **that turned out to be wrong here and is worth recording**: measured against offset, batch cost was essentially flat (55.7ms at offset 0 against 59.2ms at offset 80,000, ~6%). What the measurement did show is that an entity query costs the same whether it returns one row or five hundred — **56.1ms for one ID, 56.0ms for 500** — while the equivalent raw `SELECT` for the same rows ran in **0.03ms**. Essentially all of it is fixed per-call overhead in the entity query layer, not database work and not row work, so the fix is to make fewer calls rather than cheaper ones. ID page size and load batch size are now separate constants: `ID_PAGE_SIZE` (200) bounds the query, `LOAD_BATCH_SIZE` (10) bounds `loadMultiple()` and is unchanged, so **the 25MB-per-batch allocator spike that motivated the batch of 10 is untouched** — that finding was about loading 100 entities, never about selecting 100 IDs. The cursor is also now keyset (`id > lastId`) rather than an offset; it earns its place not by removing an O(m) walk but because bounding the scan lets the planner range scan the primary key, measured at **26.4ms against 59.2ms**. `--resume` still takes a row offset, resolved to a starting ID by one query at startup. The ascending-ID contract is unchanged, and `KeysetPaginationFunctionalTest` asserts on a 137-row corpus many batches deep that every published row is yielded exactly once in ascending order with none skipped or repeated across a page boundary, that unpublished rows and other bundles stay out, and that every resume offset lands on the right row.
- **A gather batch that loaded nothing no longer runs `resetCache()`, `drupal_static_reset()` and `gc_collect_cycles()` (`src/Service/ScoltaContentGatherer.php`).** The three ran unconditionally once per batch, about 12,397 times on a 124k-row corpus. Measured separately, `resetCache()` plus `drupal_static_reset()` cost **1.05s in total and are not worth touching**, but **`gc_collect_cycles()` cost 1664.3s — 68.4% of the entire gather, and 134ms per call**: the process holds a 168MB timestamp manifest and a 135MB page-table ledger, and a full cycle collection has to traverse that graph every time it is asked. The reset exists to stop URL alias, access result and typed data statics accumulating across a long CLI run and is genuinely needed — a generator bounds the row set, not the entity static cache — so it is kept for every batch that loaded an entity. A batch the manifest answered in full loaded nothing, has no new entity static to release, and now skips all three. On a warm build that is 99.2% of rows (122,986 of 123,957). Measured A/B over an identical 20,000-item prefix with identical partitioning (16,990 cached, 3,010 loaded in both runs): **283.4s to 121.7s, 2.33x**.
- **The build lock is renewed at every chunk boundary instead of taking a fixed 3600s lease (`src/Plugin/QueueWorker/ScoltaRebuildWorker.php`, `src/Progress/LockRenewingProgressReporter.php`).** A 3600s lease against a build measured at 2876s left roughly twelve minutes of headroom, and a slower corpus or a slower host crosses it — at which point the lock expires under a still-running build and a second one starts writing the same output directory. Raising the number trades that against a crashed build blocking the queue for an hour. Neither is necessary: the orchestrator already calls `ProgressReporterInterface::advance()` once per committed chunk, and Drupal's lock backends extend the expiry when the holder re-acquires, so the new reporter renews there. The lease now only has to outlive one chunk (300s), so **a long build never loses the lock and a crashed one frees it in minutes**.

### Fixed
- **The queue worker deleted rebuild requests it had never covered, silently dropping edits (`src/Plugin/QueueWorker/ScoltaRebuildWorker.php`).** After a successful build `drainQueue()` claimed and deleted every item in the queue. Items enqueued *during* the build describe content the build never gathered — the generator had already walked past those rows, or the entity was saved after the walk reached it — so deleting them dropped those edits permanently, with no error and no retry. ### Fixed
- **A site connected to the managed AI gateway could not authenticate, because the stored token was never decrypted before it was used (`src/Service/ScoltaAiService.php`, `scolta.services.yml`).** The token is encrypted at rest by `DrupalConfigStorage::store()` and decrypted by its `load()`. `resolveApiKey()` did not go through `load()`: it built the credentials from the raw State array, so the value that became `ai_api_key`, and with it the bearer token on every request the AI client sent, was the ciphertext. The gateway rejected it, and message, expand and summarize all failed authentication on a connection that was otherwise valid. **Model names resolved normally throughout**, because the self-heal in `createClient()` already read through `load()`, so the failure looked selective rather than total and pointed away from the credential itself. `resolveApiKey()` now reads `$this->amazeeConfigStorage?->load()`, the one path that decrypts. Nothing else about the resolution changes: an explicit `SCOLTA_API_KEY` or `$settings['scolta.api_key']` still wins and still reports its own source, stored credentials that lost are still reported as stored, and a connection whose model resolution has not completed still degrades exactly as before. When the credential store is absent (the minimal construction path, where it is an optional argument) the resolution reads as no stored credentials, which is what an empty State entry already did. The Drupal state service is no longer a constructor argument of `ScoltaAiService` or an argument in `scolta.services.yml`, because the credential store is now the only route to the credentials and nothing else in the service read state. Covered by `tests/src/Functional/AmazeeStoredTokenDecryptionTest.php`, which stores a token through the real store, confirms the stored value is ciphertext, and asserts that both the resolved key and the `ai_api_key` in the built client config are the original plaintext; it fails against the pre-fix code.
- **The key-source matrix could not pass in CI, for a reason unrelated to what it tests (`tests/src/Functional/ScoltaApiKeySourceMatrixFunctionalTest.php`).** It set `SCOLTA_API_KEY` with `putenv()` and then asserted that `/health` and the settings page agreed with the in-process resolution. There are two processes: the functional job starts `php -S` before PHPUnit runs, so the server inherits nothing the test process does afterwards, and every env-only cell resolved to `env` in process and `none` over HTTP. The matrix failed on its first row on `main`. The variable is now also written into the test site's `settings.php`, which Drupal includes on every request, so the server observes the same state the assertions describe.
- **`getApiKeySource()` reported Amazee.ai while an explicit key served every request, because reporting and resolution were two derivations with opposite precedence (`src/Service/ScoltaAiService.php`, `src/Form/ScoltaSettingsForm.php`, `src/Controller/HealthController.php`, `src/Commands/ScoltaCommands.php`, [#188](https://github.com/tag1consulting/scolta-drupal/issues/188), parent [scolta-php#252](https://github.com/tag1consulting/scolta-php/issues/252)).** Root cause: `buildConfig()` gave an explicit `SCOLTA_API_KEY` or `$settings['scolta.api_key']` priority over stored Amazee credentials and fell through to Amazee only when both were empty — its own comment said so outright — while `getApiKeySource()`, which every reporting surface called, checked `scolta.amazee.credentials` **first** and returned `'amazee'` before it had looked at the environment at all. Nothing forced the two to agree, and they did not. A site with a perfectly valid key therefore sent every request with that key while the settings form displayed "Connected to Amazee.ai (auto-provisioned free trial)" in success green, and nothing in the interface revealed which key was actually in use. **The blast radius was wider than the message**, because `isAmazeeActive()` was defined as `getApiKeySource() === 'amazee'` and inherited the wrong precedence: it also drove the provider the settings form preselected and the `scolta:status` output. This is not cosmetic — it is a diagnostic surface lying in exactly the situation where somebody reaches for it, and it has already cost a misdiagnosis. On the Athenaeum demo on 2026-07-29 the Amazee message was read as evidence that the environment variable was missing, when a 109-character `sk-ant-api03` value was present in the container the whole time and the real defect was elsewhere. **The fix is a single derivation, not two that agree.** A new `resolveApiKey()` hands the platform's explicit candidates and any stored credentials to `Tag1\Scolta\Config\ApiKeyResolver` and returns the key, its source, the effective provider and the base URL together; `buildConfig()`, `getApiKey()`, `getApiKeySource()`, `isAmazeeActive()`, `createClient()`, the key-expiry-recovery gate, the settings form, `/health` and both Drush commands all read that one answer. Fixing `getApiKeySource()` to check the environment first would have made them agree today and left them free to drift again, which is why the resolver returns the source alongside the key: there is nothing left for a caller to re-derive. **`getApiKeySource()` now returns `amazee:auto` or `amazee:operator` rather than a single `amazee`** — a trial that provisioned itself and a provider somebody selected mean different things to an operator reading a status line — and both remain distinct from `env`, `settings` and `none`. **A stored-but-overridden credential is now stated rather than hidden:** the settings form appends "Amazee.ai credentials stored but overridden by SCOLTA_API_KEY" (or by the settings.php key) and renders the whole line in the warning colour, because showing that state in success green is what let it be read as proof that Amazee was serving traffic. `/health` gains `ai_key_source` and `ai_amazee_overridden`; `scolta:status` prints the source and a full description; `scolta:check-setup` takes the resolution so its AI-key row cannot word the key differently from the settings page. Two behaviours are deliberately preserved rather than tidied: `createClient()` now guards on "nothing configured and nothing stored" instead of `source === 'none'`, so a site whose provider is `drupal_ai` — for which Amazee is ineligible and the source is therefore `none` — still does not provision a trial on top of credentials it already has; and the `drupal_ai` exclusion itself moved from a branch in `buildConfig()` to an input of the resolution, so every surface sees the same eligibility rule the config path applies. Covered by `tests/src/Functional/ScoltaApiKeySourceMatrixFunctionalTest.php`, whose four-by-two matrix drives every source with and without stored credentials against a real Drupal and asserts the settings form, the `/health` payload and the CLI row agree in every cell, and by `tests/src/ApiKeySourceSingleDerivationTest.php`, which pins the structural property instead of the symptom: nothing outside the resolver reads the credential store or `SCOLTA_API_KEY`, and all three reporting surfaces call `resolveApiKey()`. Requires the resolver added in scolta-php 1.1.0; the `tag1/scolta-php` constraint is bumped when that release is tagged.
- **An Amazee.ai gateway model alias is no longer written into the operator-facing `ai_model` ([#187](https://github.com/tag1consulting/scolta-drupal/issues/187), parent [scolta-php#251](https://github.com/tag1consulting/scolta-php/issues/251)).** Amazee model resolution returns LiteLLM **gateway aliases** (`claude-4-5-sonnet`) that only the Amazee proxy accepts. `ScoltaAiService::createClient()` wrote them straight into `scolta.settings:ai_model` and `ai_expansion_model` — the keys an administrator uses to name a provider-native model — with no guard beyond a non-empty check, so the write clobbered an explicit choice as well as the shipped default. Once the trial expired or a direct provider key was configured, `ai_provider` became `anthropic` while `ai_model` still held a name Anthropic's API does not recognise, and AI degraded permanently behind a generic `ai_error` with nothing in it for an operator to search for. Both methods now unpack `provider_id` (passed to `createInstance()`) and `model_id` (passed to `chat()`, so the admin's configured model is honored instead of an empty string). The existing `ScoltaAiServiceDrupalAiServiceLayerTest` file-inspection guards asserted the buggy shape (`->chat($input, '', …)`) and could never catch this; they now pin the array-unpacking contract (`createInstance($default['provider_id'])`, resolved `model_id`, and that the raw array is never passed to `createInstance()`). A new `ScoltaAiServiceDrupalAiBehaviorTest` adds the runtime coverage that was missing: it actually executes `messageViaDrupalAi()`/`conversationViaDrupalAi()` against a fake plugin manager returning the real `['provider_id' => …, 'model_id' => …]` shape, and fails against the array-to-`createInstance()` call while passing against the fix. The same fix also corrects the token-limit call: the third `chat()` argument is `$tags`, not options, so the previous `['max_tokens' => $maxTokens]` passed there was silently ignored and never bounded the response. `max_tokens` is now applied via `$provider->setConfiguration()` before the call (with `['scolta']` passed as the tags), and the behavior test asserts the limit lands on `setConfiguration()`, that `chat()` receives the tags, and that the requested operation type is `'chat'`.

### Known limitations
- **Facet counts do not exactly match the filtered result list once AI query expansion has run ([tag1consulting/scolta-php#265](https://github.com/tag1consulting/scolta-php/issues/265)).** The panel recounts after expansion, which it did not do before this release, and on every corpus measured it is strictly closer to the list than the previous behaviour was. It is not yet exact. It reaches this module through the vendored `js/scolta.js`. Unexpanded queries are exact. Targeted for 1.1.1; see the scolta-php issue for the diagnosis and the fixes considered.

- **Playwright layout tests** (`tests/playwright/layout.spec.js`): Three browser-level tests at 1440 px viewport asserting `.scolta-layout` fills ≥90 % of viewport width in single-column and two-column (`has-filters`) modes. Wired into CI (`playwright` job in `.github/workflows/ci.yml`).
- **Admin rebuild notice persistence**: Rebuild notices now persist in Drupal State across page loads until each admin user explicitly dismisses them. Per-user dismissal tracked via `user.data` service keyed to a unique `notice_id`; notices render via `hook_page_top()` on admin pages. Dismiss route: `GET /admin/config/search/scolta/dismiss-rebuild-notice?notice_id=…`.
- **Drupal functional test suite in CI** (`functional` job in `.github/workflows/ci.yml`): Boots a real Drupal 11 installation (SQLite + PHP built-in server) and runs all `tests/src/Functional/` tests on every push. Covers the full HTTP render pipeline, including `hook_page_top()` and controller instantiation, which unit tests cannot reach.
- **`RouteSmokeFunctionalTest`**: Reads `scolta.routing.yml` at runtime and smoke-tests every defined route — GET routes as authenticated admin (assert non-500), GET routes as anonymous (assert 302/403), POST routes with empty body (assert structured JSON 4xx). Any route added to the YAML is automatically covered on the next CI run without a manual test-list update.
- **`YamlIntegrityTest::testAllFromRouteCallsReferenceDefinedRoutes`**: Static-analysis guard that scans all `.module` and `src/` PHP files for `fromRoute('scolta.*')` calls and asserts each name exists in `scolta.routing.yml`. Catches the `RouteNotFoundException` class of bug at the unit-test level before a browser ever hits the page.

### Changed
- Inherits all scolta-php 0.2.4 fixes and features (phrase-proximity scoring, WASM config key fix, quoted-phrase forced-mode, second WASM rebuild)

### Fixed
- **Full-width search results layout**: `css/scolta.css` had `grid-template-columns: 220px minmax(0, 1fr)` as the permanent default for `.scolta-layout`, making the empty filter sidebar always occupy 220px and squeezing all results into the narrow right column. The layout now defaults to `grid-template-columns: 1fr`; the two-column variant only activates via `.scolta-layout.has-filters` (added by JS when multiple sites are indexed). Added `.scolta-filters:empty { display: none }` so the empty sidebar is hidden. Adds `LayoutCssRegressionTest` to guard against recurrence.

## [0.2.3] - 2026-04-17

### Fixed
- **Asset deployment on install**: `hook_install()` now copies compiled JS/CSS/WASM from `scolta-php` into the module directory. Composer `post-install-cmd` scripts only run for the root package, so assets were never deployed when installing as a dependency.
- **Pagefind path fix**: `ScoltaSearchBlock` was pointing `pagefindPath` at `{output_dir}/pagefind.js`; the Pagefind binary writes its output into a `pagefind/` subdirectory, so the correct path is `{output_dir}/pagefind/pagefind.js`.
- **Cache invalidation after rebuild**: All rebuild paths (Drush, admin UI form, Batch API, Queue Worker) now invalidate the `scolta_search_index` cache tag so the search block updates immediately without a manual cache flush.

### Changed
- Inherits all scolta-php 0.2.3 fixes and features (filter sidebar, N-set merge, AI context, PII sanitization, priority pages)

## [0.2.2] - 2026-04-16

### Added

- **Scoring language:** Settings form now includes a language select (30 ISO 639-1 options) stored as `scoring.language`.
- **Custom stop words:** Textarea field for comma-separated additional stop words (`scoring.custom_stop_words`).
- **Recency strategy:** Select field for recency decay function — `exponential`, `linear`, `step`, `none`, or `custom` (`scoring.recency_strategy`).
- **Custom recency curve:** Textarea for JSON `[[days, boost], …]` control points, visible only when strategy is `custom` (`scoring.recency_curve`).
- Config schema (`scolta.schema.yml`) and install defaults (`scolta.settings.yml`) updated for all four new fields.

## [0.2.1] - 2026-04-15

### Fixed

- **Security:** Validate the configured Pagefind binary path against an allowlist (`pagefind`, `npx`, `node_modules/.bin/pagefind`) before passing to `Process`. Rejects unexpected paths and logs an error, preventing command injection via a compromised config value.

## [0.2.0] - 2026-04-13

### Fixed

- **UX:** `hook_requirements()` added to `scolta.install` — shows a warning in the Drupal Status Report when the Pagefind binary is not installed and the PHP fallback indexer is active, with instructions to install the binary for full language support.

### Added

- **Install hook**: `hook_install()` queues an initial index build on install and displays a status message with instructions for immediate building via Drush.
- **Index-missing validation in search block**: `ScoltaSearchBlock::build()` checks for the Pagefind index on disk; admins see a warning with a link to build, non-admins see nothing until the index is ready.
- **Rebuild Index button**: Admin settings form at `/admin/config/search/scolta` now includes a "Rebuild Index" button that triggers an immediate index rebuild using Batch API (PHP indexer) or synchronous binary execution.
- **Batch API integration**: PHP indexer rebuilds from the admin UI use Drupal's Batch API (`ScoltaBatchOperations`) to process content in chunks, preventing timeouts on large sites.
- **Queue Worker for auto-rebuild**: New `ScoltaRebuildWorker` queue worker (`scolta_rebuild` queue) processes index rebuild requests during cron, with a lock to prevent concurrent builds.
- **Auto-rebuild on entity changes**: `hook_entity_insert()` and `hook_entity_update()` automatically enqueue a rebuild when nodes are saved and `pagefind.auto_rebuild` is enabled.
- **Uninstall cleanup**: `hook_uninstall()` cleans up the rebuild queue, build lock, and state entries when the module is uninstalled.
- **PHP indexer integration**: `scolta:build` now supports in-memory PHP indexing via `Tag1\Scolta\Index\PhpIndexer`, eliminating the need for the Pagefind binary.
- `--indexer` option on `scolta:build` to select indexer mode (`php`, `binary`, or `auto`); overrides the `indexer` config setting.
- `--force` option on `scolta:build` to skip the content fingerprint check and force a rebuild.
- `indexer` config key (`auto`/`php`/`binary`) in `scolta.settings.yml` with matching schema entry.
- Auto-detection: when `indexer` is `auto`, the build command uses the binary if available, otherwise falls back to the PHP indexer.
- Content fingerprint tracking (`.scolta-state` file) to skip unnecessary rebuilds when content has not changed.
- `wasmPath` key added to `drupalSettings.scolta` in `ScoltaSearchBlock`, pointing to the WASM glue JS file served from the module directory.
- `ai_languages` config setting for multilingual AI response support, configurable via the admin form (comma-separated language codes)
- All AI controllers now pass `aiLanguages` from config to `AiEndpointHandler`
- `PromptEnrichEvent` Symfony event dispatched before AI prompts are sent to the LLM provider
- `EventDrivenEnricher` bridging scolta-php's `PromptEnricherInterface` with Drupal's event system
- All AI controllers now inject the event dispatcher and pass the enricher to `AiEndpointHandler`

### Removed

- **Extism/FFI dependency**: All references to `ScoltaWasm`, `ExtismCheck`, `Tag1\Scolta\Wasm`, FFI, and Extism have been removed. scolta-php is now pure PHP with no native extensions required.
- FFI extension removed from CI workflow (`setup-php` no longer requests `ffi`).
- `continue-on-error` removed from CI lint step so lint failures are caught.
- `testScoltaPhpWasmPathUsesUnderscores` test removed (ScoltaWasm.php no longer exists in scolta-php).
- `isExtismAvailable()` helper and associated skip logic removed from `ScoltaSettingsFormTest` since `toJsScoringConfig()` is now pure PHP.

### Changed

- **Client-side WASM scoring**: Scoring, merging, and query expansion parsing now happen entirely in the browser via WASM instead of server-side PHP/WASM. The `wasmPath` setting is injected into `drupalSettings` so `scolta.js` can load the WASM glue module.
- WASM assets (`scolta_core.js`, `scolta_core_bg.wasm`) are now copied to `js/wasm/` by the `copy-assets` composer script alongside the existing JS/CSS assets.
- `scolta:build` Drush command now pre-resolves and caches all prompt templates (Step 3) after building the Pagefind index, reducing runtime overhead for API endpoints.
- Prompt resolution uses pure PHP (`DefaultPrompts::resolve()`) instead of WASM calls.
- Updated PHPDoc comments to remove stale references to WASM/FFI/Extism.

### Previously added

- Search API backend (`ScoltaBackend`) for Pagefind-based indexing and search
- 7 Drush commands: `scolta:build`, `scolta:export`, `scolta:rebuild-index`, `scolta:status`, `scolta:clear-cache`, `scolta:download-pagefind`, `scolta:check-setup`
- Admin settings form at `/admin/config/search/scolta` with AI, scoring, display, cache, and prompt configuration
- Search block (`ScoltaSearchBlock`) for placing the search UI in block regions
- 4 API endpoints: `expand-query`, `summarize`, `followup`, `health` at `/api/scolta/v1/`
- `DrupalCacheDriver` implementing `CacheDriverInterface` for Drupal's cache API
- Content export pipeline integrating Search API indexing with Pagefind HTML generation
- Drupal permissions: "Administer Scolta" and "Use Scolta AI features"
- Config schema and install defaults in `config/schema/` and `config/install/`
- Symlinked shared assets from scolta-php (`scolta.js`, `scolta.css`)
- Drupal behavior bridge (`scolta-drupal-bridge.js`) for Drupal.behaviors integration
